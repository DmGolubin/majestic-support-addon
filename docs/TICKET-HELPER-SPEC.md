# Помощник тикетов — правила и запрос разработчикам

Дата: 16.10.2026. Дополнение к контракту API 1.1. Это отдельный этап B; API шаблонов не получает автоматически доступ к тикетам.

## 2. Три независимых механизма

1. **Личное напоминание:** выключатель и 5/10/15 минут, звук и ссылка на свой тикет. От первого сообщения игрока без последующего ответа саппорта; дополнительные сообщения игрока не откладывают таймер. Одно напоминание за период ожидания. Ответ завершает период; новое обращение после ответа создаёт новый период.
2. **Системное напоминание:** тег бота через 20 минут по правилу владельца. Не является ответом человека, назначением тикета или подтверждением возврата. Личный интервал не изменяет это правило.
3. **Серверный возврат:** через 30 минут по правилу владельца; выполняет бот/панель, не плагин. При подтверждённом возврате/передаче/закрытии отменить напоминания прежнему ответственному. Истечение предполагаемого срока само по себе не даёт клиенту права заявлять, что возврат выполнен.

Требует подтверждения серверной команды: от какого события реально считаются системные 20/30 минут, поведение при передаче, смене статуса, ответе другого саппорта, удалении/редактировании сообщений и вложениях без текста. В API нужны рассчитанные сервером даты, а не догадки по названию ветки.

## 3. Новый тикет — самостоятельный звук

- Только новая ветка в настроенных родительских каналах MJ/RO. Другой сервер, ЛС, обычное сообщение, системный тег и возврат старого тикета не запускают звук.
- Дедупликация ID, ограничение частоты, игнорирование истории при старте/переподключении. Сигналы, подавленные во время паузы, не откладываются на потом.
- Отключаемое подавление, если именно новый тикет открыт и Discord в фокусе. Громкость, проверка звука, пауза между сигналами, список родительских ID.
- Настройки хранятся локально отдельно от библиотеки; по умолчанию выключено. Нет запросов к сайту и чтения текста обращений для этой функции.
- Автовзятия и отправки сообщений нет. Не обещать, что звук всегда быстрее штатного: обе реакции зависят от доставки события клиенту и ОС.
- Реализация v1 на исходном скрипте использует свежий ID ветки и флаг новизны, если он доступен. Если доступ к свежей приватной ветке выдан позже, а Flux не передал флаг, остаётся риск ложного распознавания; задержанные более чем на 30 секунд события намеренно пропускаются. Проверить эти случаи в Discord до закрытия B02.
- Старый TicketSound и новая функция одновременно могут дать два звука. Пользователь выбирает один обработчик; плагин не выключает другой сам.

## 4. Что нужно от разработчика панели/бота для личного таймера

Нужен авторитетный источник текущего состояния, а не только уведомление на 20-й минуте. Получив первый сигнал в 20 минут, невозможно вовремя восстановить ранние 5/10/15.

Предлагаемый read-only ресурс `GET /api/plugin/v1/tickets/assigned` (маршрут пока не существует как подтверждённый контракт): только собственные назначенные тикеты разрешённых проектов, полный снимок и ETag. Отсутствие записи в полном снимке отменяет локальное ожидание. При пагинации — одна общая ревизия.

Минимальные поля: ticketId, guildId, channelId, parentChannelId, project, assigneeAccountId, state, waitingSince, waitingCycleId, systemReminderAt, returnToPoolAt, version. Общие serverTime, accountId, revision. state различает waiting_support, waiting_player, pool и closed. waitingCycleId остаётся одним при дописывании игроком и меняется после нового периода ожидания. ID аккаунта панели должен сопоставляться с текущим /me; Discord ID не принимать за него без явного соответствия.

Пример **предлагаемого** ответа, не выгрузка действующего API:

```json
{
  "accountId": "account-example",
  "revision": "tickets-r12",
  "serverTime": "2026-10-16T10:07:00Z",
  "tickets": [{
    "ticketId": "ticket-example", "guildId": "530693013622489088",
    "channelId": "example-channel", "parentChannelId": "696711470783922247",
    "project": "mj", "assigneeAccountId": "account-example",
    "state": "waiting_support", "waitingSince": "2026-10-16T10:00:00Z",
    "waitingCycleId": "waiting-4", "systemReminderAt": "2026-10-16T10:20:00Z",
    "returnToPoolAt": "2026-10-16T10:30:00Z", "version": "ticket-v7"
  }]
}
```

События изменения тикета/назначения/закрытия/возврата — через существующий авторизованный поток, если сервер поддерживает, иначе отдельный согласованный транспорт. Событие инвалидирует снимок, клиент перечитывает его. Повторы/перестановка/пропуски не возвращают старого владельца; нет параллельных запросов. На старте, после сна и reconnect — полный снимок до включения напоминаний.

Перед звуком обязательно подтвердить актуальное назначение и ожидание сервером (условный GET допустим). При недоступной сети напоминание не выдавать как достоверное; показать состояние недоступности. Время считать от serverTime с монотонным локальным отсчётом; не полагаться на настройку часов пользователя. После установленного сервером returnToPoolAt не сигналить по устаревшему снимку, запросить состояние. Не пытаться вернуть тикет самостоятельно.

Хранить отметку показанного напоминания по аккаунту + ticketId + waitingCycleId, чтобы reload не повторял сигнал. Срок хранения и несколько устройств согласовать: локальная отметка предотвращает повтор только на одном устройстве. Общая серверная квитанция нужна только если выбран режим «одно уведомление на все устройства».

## 5. Настройки и Telegram

Для синхронизации нужен подтверждённый API чтения/изменения настроек с версией/If-Match. Предложение: раздельные поля personalReminderEnabled, personalReminderMinutes (5/10/15) и канал доставки discord; Telegram — отдельный включатель. Громкость/выход звука локальны.

Существующий Telegram threshold 10/15/20 не менять молча. Разработчик сначала подтверждает, считают ли эти напоминания тот же период ожидания. Если да — согласовать общую модель и миграцию; если нет — оставить разные виды уведомлений. Личный интервал не изменяет системные 20/30. Никакой синхронизации настроек пока нет.

Для новых ресурсов нужны отдельные минимальные права (например tickets:assigned:read и notifications:settings:read/write). Это расширение полномочий: не добавлять их молча к ранее выданному токену FAQ; согласовать повторное разрешение. Владельца и права проверяет сервер. Плагину не нужны Telegram ID, токен Telegram-бота, cookies или чтение всех сотрудников/всей переписки.

## 6. Если API отсутствует

Предпочтительно добавить read-only снимок и события поверх уже существующего учёта тикетов бота. Если панель не хранит эти состояния, источник должен дать разработчик бота — нельзя предполагать, что они уже доступны через сайт.

Клиентский разбор сообщений допустим лишь после предоставления проверенных примеров всех событий, стабильных ID ботов и способа восстановления текущего назначения после перезапуска. Упоминание в 20 минут, создатель ветки, участник ветки и последний ответивший человек не доказывают назначение. Без этого личный автоматический таймер остаётся недоступен. Ручной локальный таймер возможен как отдельный явно ручной режим, но не заменяет требование «только мои назначенные тикеты» и сейчас не включён.

## 7. Приёмка

Новый тикет: MJ/RO, старый thread join, reload/reconnect, повтор события, очередь новых тикетов, фокус, громкость 0, выключение и повторное включение плагина, отсутствие второго обработчика TicketSound. Тест аудиографа не доказывает слышимость на пользовательском устройстве.

Личное напоминание: каждый порог 5/10/15, чужой тикет, ответ до порога, ответ одновременно с порогом, вложение без текста, дополнительные сообщения игрока, тег бота, передача/закрытие/возврат в 30 минут, изменения интервала, сон/reload/offline, отзыв доступа и несколько устройств. Настройки Mini App не затираются. Нагрузка — на 20 и 100 клиентов с теми же ограничениями повторов, что в API-контракте.

Подбор шаблонов B04 остаётся следующим этапом: нужен достоверный текст исходного обращения и его источник, отдельно согласовать доступ к содержимому. Снимок ожидания намеренно не содержит переписку.
