# SupportTemplates: серверный API

Серверная часть работает в `majestic-support-site`. Коллеги разрабатывают только плагин.
Им передаются этот контракт, `docs/discord-plugin-openapi.json`, адрес тестовой панели и тестовые аккаунты с ограниченными
правами. Доступ к серверу, репозиторию панели, БД, `.env` и ключам ботов не требуется.
Публичность исходников плагина не заменяет проверку распространяемой сборки и установщика.

## Включение владельцем

По умолчанию интерфейс закрыт: `503 plugin_disabled`. Для допуска после проверки плагина
установить в окружении сервера `PLUGIN_API_ENABLED=true` и перезапустить штатным способом.
Для отключения убрать значение или поставить `false` и перезапустить сервер.
`SITE_URL` (или существующий `CLIENT_URL`) должен указывать на адрес панели с HTTPS.
Новые таблицы создаются штатной миграцией `server/initDatabase.js`, только в основной БД.
Существующие шаблоны и настройки сотрудников не копируются и не перезаписываются.

При необходимости `PLUGIN_ALLOWED_ORIGINS` задаёт список разрешённых origin через запятую.
По умолчанию: `https://discord.com`, `https://ptb.discord.com`, `https://canary.discord.com`.
Запросы без Origin допустимы для desktop-транспорта. `Origin: null` по умолчанию не получает
разрешения CORS. Подбирать origin следует по фактическому транспорту проверенного плагина,
не расширяя CORS остальных маршрутов панели. CORS не является проверкой подлинности плагина.

Секрет клиента, Discord-токен сотрудника, cookies панели и ключи ботов плагину не передаются.
Отдельного секрета подписи для этого API нет: токены случайные, в БД хранятся их SHA-256.
Владелец проверяет исходники, зависимости, установщик, сборку и способ обновления;
утверждённые версии распространяются под его контролем. Серверный токен доказывает права
подключения, но не подтверждает неизменность установленного плагина.

## Адреса и общие правила

База внешнего API: `https://panel.majestic-rp.tech/api/plugin/v1`.
Все тела и ответы — JSON; ошибки: `{ error, code, requestId }`.
У защищённых запросов заголовок `Authorization: Bearer <access_token>`.
Токены запрещены в URL, логах, экспортах и обычном JSON настроек плагина.
Долговременное хранение — через защищённое хранилище ОС; если его нет, только память
до закрытия Discord. При выходе токены и рабочие данные удаляются локально.

Проекты: `majestic` (Majestic RU) и `russia-online` (Россия Онлайн). EU не входит в первый
релиз. `accountId` — Discord ID сотрудника как строка, не региональный числовой `users.id`.
ID FAQ включают проект (`majestic:123`), поскольку числовые ID разных БД могут совпадать.
ID личных шаблонов, папок и корзины — строки с числами из общего хранилища сайта.
Таймстемпы — ISO 8601 UTC. Плагин использует время сервера, а не локальные часы для таймеров.

### Разрешения

| Scope | Доступ |
| --- | --- |
| `profile:read` | Имя, ID подключения и доступные проекты |
| `faq:read` | Чтение FAQ согласно правам аккаунта на сайте |
| `personal:read`, `personal:write` | Чтение / изменение только своих шаблонов |
| `folders:read`, `folders:write` | Чтение / изменение только своих папок |
| `sync:read` | События обновления |
| `tickets:assigned:read` | Только свои назначенные тикеты, в департаменте поддержки |
| `notifications:settings:read` | Настройки доставки и пороги из Telegram |
| `notifications:settings:write` | Только включатель доставки Discord |

Основной FAQ из плагина нельзя менять даже руководителю. Неизвестные поля записи
не принимаются. Сервер сам определяет владельца и проверяет текущие права каждого запроса.
Утрата проекта сразу убирает его данные. Увольнение блокирует и отзывает подключения
при следующей проверке; повторный приём на работу не восстанавливает отозванные токены.

## Вход

1. `POST /oauth/device_authorization`:
   `{ "client_id": "support-templates", "device_name": "Discord — рабочий ПК", "scope": "profile:read faq:read personal:read personal:write folders:read folders:write sync:read tickets:assigned:read notifications:settings:read notifications:settings:write" }`.
   `scope` можно опустить для полного указанного набора; неизвестные права отклоняются.
   Ответ: `device_code`, `user_code`, `verification_uri`, `verification_uri_complete`,
   `expires_in: 600`, `interval: 5`. `device_code` секретен; `user_code` можно показывать.
2. Открыть `verification_uri_complete` во внешнем браузере. На `/connect` сотрудник входит
   обычным способом, сверяет код, видит аккаунт, устройство и права, явно разрешает или отказывает.
   Открытие ссылки само по себе ничего не разрешает. Страница работает и с телефона.
3. Не чаще указанного интервала вызывать `POST /oauth/token`:
   `{ "client_id": "support-templates", "grant_type": "urn:ietf:params:oauth:grant-type:device_code", "device_code": "..." }`.
   Ожидание: `400 authorization_pending`; ранний опрос: `400 slow_down` — увеличить интервал
   минимум на 5 секунд; отказ/отмена: `400 access_denied`; истечение: `400 expired_token`.
4. Успех: `{ access_token, refresh_token, token_type: "Bearer", expires_in: 900, scope, connectionId }`.
   Код одноразовый, токены передаются только в теле HTTPS-ответа плагину.
5. Отмена: `POST /device-requests/cancel` с `{ device_code }`. Отмена после уже завершившегося
   обмена также отзывает выданное этой попытке подключение. Клиент игнорирует поздние ответы
   отменённых попыток и ответы предыдущего аккаунта.

Обновление: `POST /oauth/token` с `{ client_id: "support-templates", grant_type: "refresh_token", refresh_token }`.
Каждый обмен выдаёт новую пару, старая перестаёт действовать. Повтор использованного refresh
отзывает подключение (`401 session_revoked`). Клиент выполняет один refresh одновременно,
сохраняет новую пару до повторных запросов. При потере ответа refresh нужен новый вход;
не повторять старый refresh автоматически. Неактивность — 30 дней, абсолютный срок — 90 дней.

`POST /oauth/revoke` с действующим Bearer отзывает своё подключение. С истёкшим access
сначала обновить токен либо отключить устройство на сайте. В `/connect` доступны список
устройств и отключение одного/всех. Сайт использует отдельные сессионные маршруты
`/api/plugin/connect/*` с CSRF-защитой; плагину они не предназначены.

## Библиотека

`GET /me` требует `profile:read`: `{ accountId, name, connectionId, projects, scopes,
permissionsRevision, schemaVersion: 1, minimumPluginVersion: "1.0.0", serverTime }`.
Версия сообщается для совместимости, а не для доказательства доверия клиентскому коду.

`GET /snapshot` требует `faq:read personal:read folders:read` одновременно.
Ответ: `{ schemaVersion, accountId, projects, revision, permissionsRevision, serverTime,
faq, personal, folders, trash, colorLabels, limits }`. Снимок полный в пределах доступных
проектов. Отсутствующая запись удаляется из локальной рабочей библиотеки.
Персональное хранилище читается в согласованной транзакции; FAQ каждого проекта — одним
запросом к его региональной БД. Глобальной транзакции между разными БД нет; следующий
снимок компенсирует изменение FAQ во время чтения другого проекта.

* FAQ: `{ id, version, title, text, format: "html", projects, category, tags, status, updatedAt }`.
  HTML очищается сервером. Статус редактирования скрывается для сотрудников без `faq_edit`,
  как на сайте. HTML не исполнять; для вставки в Discord преобразовать в подходящий текст.
* Личный шаблон: `{ id, version, title, text, format: "text", projects, shared, command, color, folderId, updatedAt }`.
  Текст сохраняет Markdown, переменные и `[[greeting:end]]` буквально.
* Папка: `{ id, version, title, project, position, updatedAt }`.
* Корзина: `{ id, version, title, text, projects, shared, color, command, purgeAt }`.

Цвет — один из ключей `limits.colors`, либо `null`; не HEX. `limits` сообщает пределы:
название шаблона 160 символов, текст 20000, папка 120, команда 40 без пробелов и `/`.
Корзина хранится **7 дней**, как на сайте. В первой версии нет постоянного удаления.
Общие шаблоны — одна запись; изменение/удаление/восстановление такой записи требует
доступа к обоим проектам, чтобы не менять содержание отозванного проекта.

`ETag` снимка — кавычки вокруг `revision`. `If-None-Match` позволяет получить `304`.
В записях `version` — непрозрачная строка. Не вычислять её на клиенте.

| Метод | Путь | Тело |
| --- | --- | --- |
| POST | `/personal-templates` | `{ title, text, project?, shared?, command?, color?, folderId? }` |
| PATCH | `/personal-templates/{id}` | Изменяемые поля из той же модели |
| DELETE | `/personal-templates/{id}` | Переносит запись в корзину |
| POST | `/trash/{id}/restore` | Возвращает шаблон, ID новой записи может отличаться |
| POST | `/folders` | `{ title, project?, position? }` |
| PATCH | `/folders/{id}` | `{ title?, position? }` |
| DELETE | `/folders/{id}` | Шаблоны остаются без папки |

Лучше всегда явно передавать `project`; без него для создания используется первый доступный.
`shared: true` требует обоих проектов. `folderId: null`, `command: null`, `color: null` очищают поле.
Поля автоотправки и настройки браузерного расширения сохраняются сервером и не управляются
этим плагином. Успешная запись возвращает `{ template }` или `{ folder }` и `ETag` записи,
создание — `201`, изменение/удаление/восстановление — `200`.

POST создания требует `Idempotency-Key` (1–128 печатных ASCII-символов, новый UUID на действие).
Повтор того же JSON по тому же пути возвращает сохранённый результат, не создавая дубликат.
Иное тело с тем же ключом: `409 idempotency_conflict`. Хранение — минимум 24 часа.
При повторе сохранить исходный порядок полей JSON. PATCH, DELETE и восстановление требуют
`If-Match: "<version>"`. Без версии — `428 version_required`, при конфликте — `412 version_conflict`.
После конфликта перечитать библиотеку и дать человеку разрешить его; не перетирать автоматически.
Занятое название — `409 name_exists`, чужая/недоступная запись — `404 not_found`.

При потере сети несохранённое — только локальный черновик текущего аккаунта; не отправлять
его от другого пользователя. При отзыве доступа очистить рабочий кэш и черновики плагина.
Уже скопированный или отправленный человеком текст отозвать невозможно.

## Обновления

`GET /sync/events` — SSE через `fetch` с Bearer; требуются `sync:read faq:read personal:read folders:read`.
События `library.changed`, `permissions.changed`, `tickets.changed` требуют перечитывания
соответствующего снимка. `resync.required` требует полной проверки, включая старт и reconnect.
`tickets.unavailable` отключает таймеры до успешного нового снимка.
`token.expired` закрывает поток для refresh; `session.revoked` завершает сессию.

Сервер проверяет изменения и права каждые 4 секунды. При каждом подключении отправляет
`resync.required`; исторический журнал не воспроизводится, `Last-Event-ID` не заменяет снимок.
Проверка выполняется через БД, поэтому изменения видны и между серверными процессами.
Максимум два SSE на подключение и 200 на процесс. При медленном клиенте поток закрывается.
На потерю потока/429/503 — экспоненциальная задержка со случайным разбросом и `Retry-After`.
Резервный опрос снимков — раз в 60 ±10 секунд, один запрос одновременно.
После сна и перед вставкой, если последней проверке больше 30 секунд, подтвердить свежесть.
Без успешной обязательной проверки старый шаблон не вставлять.

## Напоминания

`GET /tickets/assigned` требует `tickets:assigned:read`.
Ответ: `{ accountId, revision, serverTime, checkedAt, maxAgeSeconds: 75, discordEnabled, tickets }`.
Тикет: `{ ticketId, guildId, channelId, project, assigneeAccountId, state, waitingSince,
waitingCycleId, reminderAt, reminderId }`. `state`: `waiting_support` либо `waiting_player`.
У второго поля ожидания и напоминания равны `null`.
Тексты переписки, Telegram ID и вложения в ответ не включаются.

Раннее напоминание исходит из последнего сообщения игрока без последующего ответа сотрудника.
Ответ другого сотрудника тоже завершает ожидание. Бот `557518046567333899` и системные роли
в логах не сбрасывают ожидание. Вложение без текста считается обращением. Исключения вроде
короткого «спасибо» берутся из действующего `TicketAlertsService.shouldIgnoreMessage`.
Редактирование/удаление сообщения отражается настолько, насколько его отражает источник логов;
плагин не пытается самостоятельно восстанавливать отсутствующие в БД события.

Порог читается из `telegram_notification_settings.slow_reply_interval` региональной копии
сотрудника; если не задан — **15 минут**. Сохранённые значения не меняются.
Порог редактируется в существующей Telegram Mini App. Там 15 минут доступны и при старом
списке интервалов. Плагин не имеет права менять Telegram-настройки.
Включение доставки Discord и Telegram независимо. Повтор при продолжающемся ожидании —
каждые 10 минут; `reminderId` меняется для очередного повторения. При передаче тикета,
ответе, закрытии или возврате из списка его таймер отменяется. Два проекта могут иметь
одинаковые `ticketId`: локальный ключ обязан включать `project`.

Перед звуком запросить `/tickets/assigned`, убедиться в своём назначении, `waiting_support`,
включённой доставке и наступлении `reminderAt`. Сохранить обработанный `reminderId` для своего
аккаунта, чтобы reload не дублировал звук. Между разными устройствами подтверждения доставки
не координируются; звук может прозвучать на каждом устройстве. При потере связи или `503`
сигнал не подавать. После восстановления сначала перечитать состояние.

Источник — общий фоновый снимок, обновляемый каждые 30 секунд. Это задержка наблюдения,
не обещание мгновенно видеть изменения Discord. Снимок старше 75 секунд считается недостоверным
и возвращает `503 ticket_state_unavailable`, а не пустую очередь.
Существующие системные действия Discord на 20/30 минутах этим кодом не изменяются;
момент возврата в пул не угадывается по часам, он определяется фактическим назначением.

`GET /notification-settings` требует `notifications:settings:read`:
`{ version, discordEnabled, thresholdSource: "telegram", projects: [{ project, personalReminderMinutes, telegramEnabled }] }`.
`PATCH /notification-settings` требует `notifications:settings:write`, `If-Match` и тело
`{ discordEnabled: true|false }`. Остальные поля отклоняются. Громкость остаётся локальной.

### Нагрузка на игровую БД

Пользовательские API и SSE не обращаются к MySQL. Один фоновый проход на регион за 30 секунд
берёт назначенные открытые тикеты за последние 5 дней (как прежняя проверка напоминаний),
затем последние сообщения пакетами до 250 ID. Полные переписки не загружаются.
Предел — 2000 тикетов на регион; превышение не публикует обрезанный снимок.
Запросы идут последовательно через существующий background pool, с лимитом выполнения 3 секунды
и таймаутом 4 секунды. Пулы не увеличиваются. Между процессами проходы координируются advisory
lock PostgreSQL; ошибки включают паузу 2 минуты и запрет использования устаревшего состояния.
Тикеты старше окна не входят в ранние напоминания; это сохранённая граница существующего сервиса.
Telegram RU/РО при включённом интерфейсе использует тот же подготовленный снимок; проверка раз в минуту,
повтор доставки не чаще раза в 10 минут. Без включения API сохраняется прежний расписанный расчёт.

## Проверка и выпуск

`node server/scripts/localdb.js up` запускает локальные БД. Затем
`node server/scripts/verify-plugin-api.js` проверяет API на временных схемах локальных
PostgreSQL :5433 и MySQL :3309; они удаляются в конце. Тест не загружает production `.env`.
Также выполнить `npm run verify:regions`, `npm run verify:ext-gateway`, `npm run build`.

Приёмка с настоящим плагином: вход/отказ/отмена, защищённое хранение, отзыв устройства,
увольнение и потеря проекта, изменение шаблона одновременно с сайтом, потери сети и сна,
переходы тикетов и звук, независимость переключателей Telegram/Discord.
Проверить фактический установщик и сборку, HTTPS/CORS, отсутствие буферизации SSE на прокси.
Длительная нагрузочная проверка на тестовом хостинге: 20/100 клиентов, 30 минут, правки,
массовое восстановление, p95 задержки, ошибки, CPU/RAM и время фоновых MySQL-запросов.
Короткий локальный тест конкурентных запросов не заменяет эту приёмку на хостинге.

Страница `/connect` состоит из явного подтверждения кода и списка устройств. Отдельный
обучающий тур не нужен: действия одношаговые, права и последствия показаны на самой странице.
Она зарегистрирована в общей навигации и локализована в пространстве `pluginConnect` (RU/EN).
