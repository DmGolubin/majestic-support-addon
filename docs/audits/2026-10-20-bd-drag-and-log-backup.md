# BetterDiscord: перетаскивание и резервная копия логов

## Объём

По запросу владельца исправляются оставшиеся задержки при перетаскивании и предупреждение резервной копии. Новые изменения передаются Дмитрию через PR; слияние и выпуск для сотрудников не выполняются автоматически. Canary используется для проверки, Stable не изменяется.

## Причина и исправление

Живой CPU-профиль .37 (`scripts/qa/runs/a31-baseline.json` и `.cpuprofile`) показал синхронные вызовы `lstat`/`realpath`/`inspect`/`safeDirectories` из сохранения диагностики на главном потоке BD. При четырёх проходах по 90 перемещений зафиксированы long tasks 84/79 мс, максимальный интервал кадра 83.5 мс, p95 8.5 мс.

Операции основного файла BD и резервной копии теперь ожидают окончания pointer-жеста и 150 мс покоя. Очередь основного журнала остаётся ограниченной; после жеста записи продолжаются с уступкой очередного такта между сохранениями. Отпускание мыши, Escape, pointercancel, потеря захвата, blur и unmount освобождают блокировку. Проверки файловой системы не ослаблялись и не кешируются.

Независимое review выявило одновременное пробуждение двух писателей (основного файла и backup). Исправлено: каждый ожидающий получает отдельный такт, перед следующим проверяется новый жест. Регрессионный тест сначала воспроизвёл выполнение обеих записей до pointer-задачи, затем подтвердил перенос второй записи до окончания нового жеста.

Резервная копия переведена с отсутствующего в BD `window.localStorage` на хранилище платформы (`BdApi.Data` в BD, DataStore в Vencord). Обычные изменения объединяются в последнее состояние раз в 5 секунд; изменения записи/opt-out и остановка обрабатываются приоритетно. Один незавершённый снимок и один ожидающий ограничивают очередь. Ошибки остаются видимыми до подтверждённого восстановления. Предыдущий localStorage читается только для миграции, если записи платформы ещё нет.

## Промежуточная живая проверка

В candidate .38 тот же жест дал p95 8.5 мс, максимум 41.7 мс, long tasks отсутствовали; положение восстановлено через Escape. Это измерение одного клиента, не гарантия времени кадра во всех условиях.

Видимый блок логов не содержит предупреждений. Файл конфигурации BD действительно содержит резервный снимок schema 1 (1586 событий, 217768 символов), основной `main.log` дописывается с сохранением исходного префикса, `deliveryLost=0`. Отдельный idle-прогон всё ещё показывает синхронные записи 176/90 мс после окончания взаимодействия: исправление убирает их из перетаскивания, а не превращает bridge BD в асинхронную файловую систему.

Обе проверки типов прошли. Первый полный прогон обнаружил неподключённый новый модуль в двух VM-фикстурах UI; фикстуры дополнены реальной зависимостью. Следующий параллельный прогон: 2504 успешных теста, два сбоя — timeout файлового benchmark и ошибка настоящего Windows DPAPI. Проверка типов в это время выполнялась параллельно; для проверки влияния нагрузки запущен полный последовательный прогон без неё. Лимиты и проверки безопасности не ослаблены.

Same-bundle stop/start сохраняет порядок backup-записей и последнюю настройку отключения записи. Перекрывающиеся независимые экземпляры bundle при hot reload не координируются этим модулем; окончательная живая проверка использует полный перезапуск Canary.

Финальный прогон, повторный запуск и точная сборка фиксируются ниже после завершения.
