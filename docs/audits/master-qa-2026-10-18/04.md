## M04-01 — P1: unterminated whitespace tokens block snapshot loading and insertion

**Evidence:** `src/core/tokens.ts:8`, `:24`, `:55`; duplicated grammar in `src/core/panelCatalog.ts:205`, `:208` and `src/vencord/panelHtml.ts:25`, `:28`. The overlapping whitespace/name quantifiers retry many partitions of the same whitespace when `}}` is absent. This is synchronous CPU work, not a rejected promise.

**Reproduction:** `fieldsOf("{{" + " ".repeat(600))`, `fill(theSameText, {}, env)`, and `htmlToDiscordText(theSameText)` each exceeded a 1,500 ms VM deadline. At 300 spaces, observed `fieldsOf` 963 ms and `fill` 894 ms. Even 602 characters are far below all relevant text limits.

`tests/masterCodeAudit.test.ts:33`, `:36`, `:39`, `:42` reproduce the affected entry points with 20,002 characters and a 1,000 ms VM deadline, including **complete valid synthetic snapshots for both text and HTML FAQ**. A separate control at `:46` verifies the snapshot metadata is valid. This is not just a regex copied into a test: the real exported functions run.

**Reachability/impact:** `panelCatalog.ts:256` permits 1,000,000 FAQ characters and `:259` invokes these parsers; `ui/panel.ts:267` runs snapshot parsing synchronously during library loading. `ui/flow.ts:107` and `:129` run the same grammar before insertion. A malformed FAQ can therefore stall library loading without a click on that FAQ. Renderer unresponsiveness follows from the synchronous call path; no live Discord stall was induced. P1 because a very small accepted input can occupy the renderer for seconds or longer, and normal promise cancellation cannot interrupt it.

**Minimal fix:** replace backtracking token discovery with bounded scanning of delimiter positions and parse each candidate once; preserve valid defaults/options and literal malformed input. Apply equivalent behavior to all three grammar copies (or share a scanner where bundling permits). A length cap alone does not fix the 602-character case. Keep these regression inputs after replacing `.fails` with normal tests.

## M04-02 — P2: unmatched single braces cause quadratic search normalization

**Evidence:** `src/core/text.ts:11` uses `/\{[^}]*\}/g`. With no closing brace, each opening brace rescans the remaining suffix. `src/core/search.ts:24` and `:26` normalize title and full body before matching; `src/vencord/ui/Window.tsx:161` calls search during rendering.

**Reproduction:** `hard("{".repeat(10000))` took 149 ms; 20,000 took 592 ms; 40,000 and 80,000 each exceeded the 1,500 ms deadline. This approximately fourfold cost on doubling the completed inputs supports the code-level quadratic analysis.

The integrated case uses a valid FAQ body `"{x".repeat(50000)` (100,000 characters, no `{{` opener, so independent of M04-01). `parseSnapshot` accepted it in 4 ms. Searching that resulting catalog with `"answer"` exceeded the reproduction's 1,000 ms deadline. See `tests/masterCodeAudit.test.ts:50` and `:54`.

**Impact/priority:** first nonempty search over an affected catalog blocks synchronous rendering; the weak cache helps only after normalization finishes. P2: requires a substantially larger malformed body than M04-01, but remains below the permitted FAQ size and is accepted by the real catalog parser.

**Minimal fix:** replace unmatched-brace rescanning with a linear delimiter pass that preserves unmatched text. Ensure the scanner does not repeatedly call `indexOf` for an absent closer from every opener. Test both direct normalization and actual search over a validated catalog.

## M04-05 — P2: Markdown preview repeatedly scans the suffix for unclosed emphasis

**Evidence:** `src/vencord/ui/markdown.tsx:31` scans to the end for every candidate single-marker closer; `:71` calls it afresh for each opener; `:87` executes parsing synchronously in `useMemo`. For `"*x ".repeat(n)`, every candidate closing asterisk has whitespace immediately before it, so none closes, but each opener scans all subsequent characters.

**Reproduction:** executing the actual transpiled component with inert React/useMemo stubs gave:

| Input characters | Observed elapsed time |
| --- | --- |
| 3,000 | 47 ms |
| 6,000 | 178 ms |
| 12,000 | 746 ms |
| 24,000 | exceeded 1,500 ms VM deadline |

`tests/masterCodeAudit.test.ts:86` uses `"*x ".repeat(20000)` (60,000 characters). The real snapshot parser accepted this string in 2 ms; the real Markdown function exceeded the 1,000 ms deadline. These are Node measurements of parser execution, not browser frame benchmarks.

**Reachability/impact:** full body reaches `<Markdown>` in `src/vencord/ui/Preview.tsx:54`; personal editor/card consumers also pass their text at `PanelPersonalLibrary.tsx:216` and `:247`. Existing 20,000-character personal text and 1,000,000-character FAQ limits do not prevent expensive work. P2 because viewing/editing suitably malformed content can block the UI, with larger input required than M04-01.

**Minimal fix:** compute valid delimiter pairings in one pass or keep indexed delimiter positions/failure information so each failed opener does not rescan the suffix. Retain literal output for unclosed emphasis and the existing escape/word-boundary rules. No dependency change is required.

## M04-03 — P3: oversized date/time offsets insert `NaN` text

**Evidence:** `src/core/tokens.ts:10` accepts an unbounded digit sequence as a builtin; `:41` computes an unchecked millisecond shift; `:42` constructs an invalid Date; `:19`, `:20`, `:43` format its NaN components. `fieldsOf` skips these tokens as builtins, so the user is not asked to repair a field.

**Reproduction:** with a valid `env.now`, filling

```text
{{date+999999999999999999999d}} {{time+999999999999999999999h}}
```

returns exactly `NaN.NaN.NaN NaN:NaN`, with no exception. See `tests/masterCodeAudit.test.ts:60`. `src/vencord/ui/flow.ts:129`, `:232`, `:245` pass that result toward insertion.

**Priority rationale:** definite incorrect output, but it requires an extreme authored offset; no observed production occurrence and no crash. P3.

**Minimal fix:** require finite representable shifted timestamps before formatting. Preserve the invalid source token or provide controlled validation feedback rather than formatting Invalid Date. If introducing a thrown validation error, also handle it in asynchronous insert/compose consumers; currently preserving the literal avoids adding a new rejection path.

## M04-04 — P3: Unicode lowercasing invalidates highlight offsets

**Evidence:** `src/core/text.ts:8` claims length-preserving normalization but `"İ".toLowerCase()` expands into `i` plus combining dot. `src/vencord/ui/highlight.tsx:11` searches the expanded string, while `:12`, `:14`, `:20` apply those indices to an array and slices sized to the original text.

**Reproduction:** search a template titled `İx` for `x`. Search returns a hit with token `x`; `soft("İx")` is `"i\u0307x"`, length 3 instead of 2. `nqHighlight("İx", ["x"])` returns only an unmarked span containing `İx`; expected `x` is marked. Real function executed with inert JSX stubs in `tests/masterCodeAudit.test.ts:65`. User-facing consumers: `src/vencord/ui/Window.tsx:90` and `:95`.

**Priority rationale:** a visible highlighting defect for accepted Unicode titles/text; matching and insertion remain available. P3, with no claim of broad Cyrillic regression.

**Minimal fix:** map normalized positions back to source code-unit spans, or introduce a length-preserving normalization policy consistently for matching/highlighting. Do not just enlarge the marks array: source slicing would still use incorrect offsets.

### Fixes and current evidence

- **M04-01:** `src/core/tokens.ts:18` introduces a forward scanner that caches the nearest `}` and stops retrying token candidates once no closer exists. A sticky token expression without overlapping whitespace quantifiers runs only when that nearest closer forms `}}`; trimming happens after capture. Failed overlapping openers remain searchable (`{{|}}` retains its original caret behavior). Existing token grammar, nested opening braces, defaults/options and literal replacement values are preserved. `fieldsOf` uses a Set at `:46` for distinct field names. The FAQ text path uses the same scanner at `src/core/panelCatalog.ts:214`; `src/vencord/panelHtml.ts:25` keeps an equivalent local scanner so the converter remains independently consumable without core-path imports.
- **M04-02:** `src/core/text.ts:11` scans complete brace spans once and keeps the unmatched suffix literal when there is no closer. Existing normalization output is preserved, including legacy nested-brace behavior; this fix does not broaden matching semantics. `search.ts` benefits through its existing `hard` calls.
- **M04-03:** `src/core/tokens.ts:68` checks the shifted Date before formatting. An unrepresentable offset remains the exact source token, including its whitespace, instead of becoming NaN text. This adds no rejection path to async insertion consumers. Valid date/time offsets remain covered by functional regressions.
- **M04-04:** `src/vencord/ui/highlight.tsx:15` creates source-span mappings only when Unicode casing changes the length. Normalized matches then mark original character spans, including partial matches within an expanded `İ`; unchanged-length text retains its previous path. Empty query tokens are skipped instead of entering a zero-step index loop. `soft` behavior is unchanged; its inaccurate length guarantee was removed from the comment.
- **M04-05:** `src/vencord/ui/markdown.tsx:36` remembers a single-marker suffix scan that found no closer. The per-parse Set at `:47` prevents later openers from rescanning that same suffix. Successful matching, escaping, word boundaries, nested styles, links and code paths remain intact. This is a local cache addition, not a Markdown parser replacement.
