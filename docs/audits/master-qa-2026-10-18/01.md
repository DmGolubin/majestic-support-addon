## ARCH-01 — ошибка каталога очищает сессию (известная C08)

**Статус:** code-proven, уже в roadmap C08; не новый дефект. **Приоритет:** средний — потеря сохранённого входа и необходимость повторной авторизации, без доказанной утечки данных или нарушения server-side прав.

**Условие:** активная сессия получает успешный HTTP-ответ snapshot с некорректной структурой, например `faq: null`, при корректной идентичности аккаунта. Это можно отделить от 401/403, отзыва и несовпадения account/connection.

**Цепочка доказательств:**

1. `src/core/panelCatalog.ts:73` выбрасывает обычный `Error` при нарушении структуры; parser вызывается в `src/vencord/ui/panel.ts:267`.
2. `src/vencord/ui/panel.ts:305–320` блокирует доступ, но затем считает transient только определённые `PanelError`. Обычная ошибка parser попадает в `terminateSession`.
3. `src/vencord/ui/panel.ts:108–113` вызывает `active.cancel()` и `wipe()`.
4. `src/core/panelClient.ts:301–313` очищает локальную сессию/vault; реальная операция `vault.clear()` находится в `src/core/panelClient.ts:497–503`.
5. Существующий тест `tests/panelIntegration.test.ts:485–495` объединяет identity mismatch и malformed payload и прямо ожидает cancel для `faq: null`. Тест прочитан, в этой роли не запускался.

**Последствие:** сбой валидации данных нижнего слоя вызывает разрушительное действие слоя авторизации. Повторно получить исправленный каталог без нового входа уже нельзя. Это не доказательство отзыва серверной сессии: `cancel()` не равнозначен OAuth revoke уже выданной пары; подтверждена именно локальная очистка.

**Минимальное исправление:** выделить ошибку структуры/содержимого каталога из identity/auth ошибок. При ней сохранить credential/session, оставить каталог недоступным для вставки и напоминаний, показать безопасную ошибку с возможностью перечитать snapshot. Не ослаблять terminal handling для account/connection mismatch, 401/403, revocation и небезопасной ротации. Полное разделение модулей или переписывание PanelClient не требуется.

**Регрессия:** после успешного входа вернуть snapshot того же аккаунта с `faq: null`; проверить отсутствие `cancel`/`vault.clear`, заблокированные insert/reminders и возможность восстановления валидным snapshot без нового device flow. Отдельно сохранить проверки очистки для чужого account/connection, 401/403 и revoked. Задержанный результат старой сессии после logout не должен восстанавливать доступ. Текущую объединённую таблицу identity/malformed в тесте следует разделить.

## Ограничения переносимости, не новые дефекты

**Code-proven:** `platform.ts` не является полной границей платформы. Перенос только этого файла в BD не обеспечит запуск: UI импортирует Vencord React/hooks, panel получает Discord stores напрямую, renderer vault требует VencordNative, entrypoint использует ChatButtons/Settings. Минимальная будущая работа по I02/X01 — определить адаптерные входы для host React/rendering, identity/events и secure vault, затем реализовать BD entrypoint. Для текущих Vencord/standalone это ожидаемая зависимость, а не причина срочного рефакторинга. Проверка будущего адаптера должна доказать отсутствие Vencord imports/globals в его bundle и выполнить собственную lifecycle/identity/storage матрицу; детали принадлежат роли 02.

**Hypothesis, не находка:** исключение стороннего subscriber или синхронного host API после частичной регистрации могло бы оставить неполный lifecycle. В этом bounded review конкретный достижимый источник такого исключения вне Q09 не установлен. Не присваивать severity и не создавать задачу только по отсутствию общего try/finally.
