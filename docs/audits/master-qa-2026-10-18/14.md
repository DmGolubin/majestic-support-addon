## 14-01 — P2, fixed: stop discarded accepted queued writes

**Original code proof:** baseline ticketSound.ts lines 42 and 60 gated the actual storage writes on `running && gen === lifecycle`. Stop incremented lifecycle. Therefore accepted but not yet started writes became successful no-ops, while a restart read the older saved value.

**Executed baseline reproduction:** hold volume 1's write, enqueue volumes 2 through 100, then stop/start and release the first write. Actual baseline: 100 accepted updates, **one write, 99 discarded changes, reloaded volume 1, no error**. Resetting saved custom audio immediately before stop/start similarly made **zero writes** and restored the old custom sound. These were deterministic runtime reproductions, not hypotheses.

**Priority rationale:** P2 because pending local preferences could silently revert during runtime stop/start. Requires pending IO; no evidence of remote/template loss or unconditional failure.

**Minimal fix:** [options queue, line 43](../../../src/vencord/ui/ticketSound.ts#L43) and [audio queue, line 59](../../../src/vencord/ui/ticketSound.ts#L59) persist already accepted snapshots independently of playback generation. Existing generation checks still prevent stale UI/error publication, file decode and playback. Restart continues to await the queues before reading saved records.

**Regression evidence:** [100-change stop/start, line 273](../../../tests/masterPersistenceStress.test.ts#L273) now asserts **100 writes and reloaded volume 100**. [Reset immediately before stop, line 287](../../../tests/masterPersistenceStress.test.ts#L287) asserts **one audio-null write and standard sound after restart**. The previous `customSound.test.ts` cancellation expectation was corrected: [line 306](../../../tests/customSound.test.ts#L306) now verifies that a reset queued behind a failed custom save still writes null after stop, with **two attempted writes** and no stale error publication.

## 14-02 — P2, fixed: failed read allowed overwriting unread preferences

**Original code proof:** baseline loadSettings caught an options-read failure, installed defaults, then set `loaded: true`. setTicketSound merged a patch into those defaults and wrote the whole record. TicketSettings enabled edits based solely on loaded.

**Executed baseline reproduction:** valid saved enabled/channel/cooldown/quiet settings, one rejected options read, then a volume-only edit. Baseline made one full-record write replacing the unread settings with defaults and erased the read warning. A fresh-module reload confirmed the replacement.

**Priority rationale:** P2 because a recoverable read failure plus an unrelated allowed edit erased valid local configuration, including enabling/channel choices. No claim that this caused the original Q09 startup incident.

**Minimal fix:** [loadSettings, line 255](../../../src/vencord/ui/ticketSound.ts#L255) tracks successful options reading locally; [line 300](../../../src/vencord/ui/ticketSound.ts#L300) publishes loaded only on success. Existing setter/import/reset/playback guards and the existing disabled fieldset then prevent edits or playback from fallback settings. Malformed-but-readable records still follow the existing normalization policy; IO failures are not treated as empty records.

**Explicit recovery path:** [retry helper, line 307](../../../src/vencord/ui/ticketSound.ts#L307) retries within the same lifecycle. It deduplicates pending reads and ignores calls when stopped or already loaded. [TicketSettings, line 70](../../../src/vencord/ui/TicketSettings.tsx#L70) displays **«Повторить загрузку настроек»** outside the disabled fieldset after failure. During retry, the error/button clears and loading status appears; repeated failure offers retry again. This avoids recreating the runtime or invalidating its original stop callback. Audio-only read errors retain their existing independent behavior.

**Regression evidence:** [line 298](../../../tests/masterPersistenceStress.test.ts#L298) asserts zero writes after an attempted edit following read failure, original record intact, successful explicit retry restoring all preferences, then exactly one volume-only update preserving every other field. A fresh module reload confirms it. The original stop callback still stops the runtime after retry. [Line 322](../../../tests/masterPersistenceStress.test.ts#L322) covers repeated failure, duplicate retries yielding one pending read, blocked writes/playback while pending, and ignored completion after stop. [Component test, line 44](../../../tests/ticketSettings.test.ts#L44) executes production TicketSettings with synthetic JSX and verifies button placement outside disabled controls, dispatch and visibility during loading/recovery.

## Role05 follow-up — guarded host dispatcher integration

The user requested the direct dispatcher guard after role05 identified failures in subscription/cleanup. [Unsubscribe, line 316](../../../src/vencord/ui/ticketSound.ts#L316) and [subscribe, line 334](../../../src/vencord/ui/ticketSound.ts#L334) now combine optional method access with try/catch around the complete access/call, including lazy export/property resolution. Subscription failure leaves settings/manual playback usable; unsubscription failure cannot prevent subsequent audio cleanup.

[Runtime matrix, line 103](../../../tests/masterPersistenceStress.test.ts#L103): seven cases — healthy, absent dispatcher, missing methods, throwing methods, throwing unsubscribe after successful subscribe, throwing method proxy, and throwing export getter. Each runs start, plays custom audio, starts again to retire the old runtime, plays again, and calls stop twice. Each asserts **two contexts closed once each and two sources stopped once each**. Healthy and throwing-method cases assert two subscribe/two unsubscribe attempts. Five unavailable-host cases were observed failing before the guard; all seven final cases pass. Platform adapter changes remain role05-owned.

Without a functioning dispatcher, automatic thread events are unavailable. These guards do not claim to restore missing host capabilities or guarantee removal of a host listener if the host's unsubscribe itself fails.

## Limits

- Synthetic storage with structured cloning, fake AudioContext, inert host dependencies. The actual runtime and observable are transpiled/executed; production preferences adapter and Store are directly imported. No source-pattern-only substitute for runtime behavior.
- Component test uses synthetic JSX/host data; no browser layout or live Discord click acceptance. No audible playback or codec-fidelity claims.
- Same-module stop/start drains accepted writes while the JavaScript realm remains alive. Abrupt renderer/process destruction, OS crash, real IndexedDB, and cross-window contention are not tested or guaranteed. Fresh-module reload tests reuse synthetic durable storage after writes settle.
- No production API calls, real Discord mutation, token reads, dependency installation/update, build, installer suite, commit or roadmap edit. Full-suite/typechecks and deployment remain parent-coordinated. Parent startup recovery and role05 platform changes were preserved.
