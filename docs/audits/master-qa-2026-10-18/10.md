## Boundary evidence and code proofs

### Fixed destinations, authorization links, and transport

- `src/core/panelProtocol.ts:100–121`: HTTPS origins reject credentials/path/query/fragment; API paths reject absolute URLs, traversal, query strings, and backslashes. Confirmation links accept only the configured panel origin, or the explicit public-site origin for production, `/connect`, and one matching user code. The public confirmation URL is expected authorization data, not an access/refresh token URL.
- `src/core/panelTransport.ts:93–127`: the bearer token is placed in `Authorization`, cookies are omitted, redirects are errors, and cache/referrer are disabled. A redirected response or changed response URL is rejected as well. Body reads are bounded and decoded strictly at lines 123–163. Error bodies contribute only an allowlisted code at line 162; arbitrary server text is not propagated.
- `src/core/panelEvents.ts:104–165`: SSE uses the same fixed origin, header-only bearer, omitted cookies, redirect rejection, and bounded JSON error handling. Its byte parser limits frames to 64 KiB and recognizes a small event-name set (`:16–96`). Payloads do not become URLs or HTML. The UI handles event names and ignores payload content (`src/vencord/ui/panel.ts:144–157`).
- `src/vencord/panelPermission.ts:20–32`: automatic restore does not request additional CSP permission; interactive permission is limited to the panel origin and `connect-src`. Standalone declares that same host in `standalone/runtime/ipc.ts:10–15`.

Negative code proof: a path such as `/me?token=x` fails endpoint validation before fetch; an API error with arbitrary secret text fails the error-code allowlist. These were traced in source, not sent to any server.

### Session, account, and mutation boundaries

- `src/core/panelClient.ts:75–80,181–219,396–402`: login requests defined scopes, token responses are parsed, unknown scopes are rejected, and non-PanelError exceptions become a fixed transport error. OAuth token material stays in private client state and the optional protected record.
- `src/core/panelClient.ts:260–280`: mutations capture their input, derive the required scope, and recheck that scope plus the caller guard before dispatch. `src/core/panelProtocol.ts:23–60` restricts writes to personal templates/folders/trash restore or the notification switch. FAQ write paths are excluded. The notification body must contain exactly one boolean `discordEnabled` field; Telegram thresholds cannot be sent through that mutation path.
- `src/vencord/ui/panel.ts:233–267,282–300`: profile connection/account is matched to the client/current Discord user; account is rechecked after asynchronous reads. A permissions change clears the old catalog before accepting a replacement. `src/core/panelCatalog.ts:217–224` additionally matches snapshot account, rights revision, project set, and read scopes.
- `src/vencord/ui/panel.ts:441–455,478–485`: personal writes recheck account, session epoch, catalog generation, profile scopes, permitted project/shared status, and freshness. The server remains responsible for ownership/ACL enforcement on every request; client guards alone cannot prove server security.
- `src/core/panelClient.ts:437–461`: refresh first persists a rotating marker, requires an unchanged connection/scope set and a new token pair, and terminates an uncertain rotation. `:497–537` serializes/fences storage writes and cleanup. Logout clears local credentials and reports remote revocation failure (`:316–335`; `ui/panel.ts:541–545`).

Negative code proof: adding `personalReminderMinutes` to a notification PATCH, or using a FAQ PATCH, reaches `invalid()` in mutation validation before transport. A changed account or permission generation fails the UI write guard. This does not establish how a malicious third-party HTTP client would be handled by the server.

### Vault trust and persistence

- `src/vencord/native.ts:33–43`: IPC requires a live top-level main frame, one of three explicit HTTPS Discord origins, and agreement with the sender URL. `:47–67` binds persistence to the application profile/origin namespace and one live WebContents owner; `:76–87` rechecks trust/frame/URL after an asynchronous load before returning decrypted data.
- `src/vencord/panelVaultLock.ts:16–23`: the namespace derives from the normalized real application profile path and supported Discord origin. `:94–146` serializes ownership through exclusive gate/lock files and recovers an owner only when its PID is verified dead.
- `src/vencord/panelVaultNative.ts:14–16,98–126`: account names are numeric bounded snowflakes; paths cannot be supplied over IPC; unavailable encryption and unsupported Linux backends fail closed. `:128–153` bounds ciphertext/plaintext, rejects symlinks, and verifies the envelope account. `:157–184` encrypts before writing an exclusively created temporary file and renaming it. Errors are generic.
- `src/core/panelClient.ts:469–483` validates origin/client/account binding again when restoring the decrypted record. `src/vencord/panelVault.ts:42–72` preserves account-specific queue identity and snapshots writes before asynchronous IPC dispatch.

Trust-model limit, not a newly discovered bypass: native storage explicitly trusts the Discord renderer, not individual scripts/plugins inside it (`native.ts:31–32`). The account parameter is a storage selector, not an independent native assertion of the currently logged-in Discord identity. A compromised trusted renderer is outside the isolation these functions provide. No renderer compromise was established.

### Reminder data and delivery

- `src/core/panelReminders.ts:149–176` rejects a foreign account, foreign assignee, inaccessible project, stale/future check time, duplicates, and invalid state combinations. Guild/channel/ticket IDs are expected API metadata; their presence is not evidence of a token leak.
- `:232–269` binds work to account/projects/session/permission revision and checks freshness across request time; `:314–339` persists a deduplication receipt before calling audio, then rechecks generation/context/freshness. The receipt consists of account/project/ticket/reminder IDs, not ticket text or bearer credentials. These identifiers are still local metadata and should not be described as anonymous.
- `src/vencord/ui/ticketReminders.ts:40–77` requires the reminder scopes and a current binding; the notification shown is generic. `:108–139` stops delivery while changing the Discord toggle and checks the result before resuming. `src/vencord/ui/panel.ts:147–156` clears/stops or invalidates reminder work on revocation, expiry, and permissions resync.

No proof of ticket reassignment, automatic Discord message sending, or Telegram threshold writes was found in these reminder paths. Live delivery and server-side assignment authorization were not tested.

### Dynamic rendering and retained data

- `src/vencord/panelHtml.ts:7–8,78–90,93–162` converts legacy HTML using string scanning, omits active subtrees, and permits only HTTP(S) links without credentials. It never creates a DOM/parser/resource load. It is a text converter, not a sanitizer for future HTML insertion.
- `src/vencord/ui/markdown.tsx:9–10,47–97` constructs React elements and literal strings. Preview links are spans, and template title/body are rendered through React/Markdown in `Preview.tsx:42–54`. The inspected source scan found no executable HTML sink in these paths.
- `src/core/panelCatalog.ts:141–156` maps supported color keys to fixed hex values; unknown allowed keys receive no legacy color. `ColorPicker.tsx:39–40` uses data attributes and React text, not constructed HTML/CSS from the label.
- `src/core/panelPreferences.ts:62–130` projects only bounded IDs, counters, binds, and display preferences before writing. Catalog bodies and credential fields are not persisted by that adapter. `PanelPersonalLibrary.tsx:36–48` retains drafts only in memory, bound to catalog generation/account/connection, and discards them when that binding changes.

## Privacy observations and hypotheses — not confirmed vulnerabilities

1. **Diagnostic output is not content-free.** `debug.ts:111–115` sends event objects to both its ring and console; `:200–205,331–340,423–449` include search queries in snapshots/performance output/export. `inline.ts:41,78–85` also logs a chat-derived query when it matches a suggestion. This is a deliberately supported search exception (`tests/debug-privacy.test.ts:82–85`), distinct from ordinary password/composition key masking (`debug.ts:468–479`). Names, titles, IDs, and searches may be sensitive user content, but there is no demonstrated path automatically logging the panel bearer/refresh pair. Optional minimization: export query length/result count instead of query text if a stricter diagnostic privacy policy is desired. Do not call present reports anonymous or guarantee that user-entered secrets cannot appear in them.
2. **Raw non-panel exceptions remain a hardening opportunity.** `platform.ts:24,30` logs insertion/clipboard exceptions; `Host.tsx:54–55` logs a renderer exception and its message. The code proves unfiltered exception sinks, but the reviewed call paths do not prove an actual credential-bearing exception reaches them. An invented exception containing a token would not establish a production leak. Optional minimal hardening is fixed error categories for these sinks, with a regression using synthetic private exception text. No such patch or test was made here.
3. A malformed/cached response being readable over an authorized API, or IDs in preference/reminder records, is not by itself evidence of privilege escalation. Production ACLs, live TLS/redirect infrastructure, actual OS encryption availability, other plugins, and installed preload/runtime exposure remain unverified. Same-user filesystem attacks and malicious co-resident renderer code were not reproduced.
