## Verified finding

**R17-01 · P2 — pluginCommit does not attest to the copied build inputs.**

Code proof: `standalone/build.mjs:28-31` copies plugin/core/runtime/compile files from the live working tree; `:57` separately reads the live loader; `:69-70` records only `git rev-parse HEAD` as pluginCommit. No tracked/untracked-input cleanliness check or source digest binds those copies to HEAD. `:75` copies the recipe later, so concurrent modifications can also make the recipe differ from the earlier compiled inputs. This is a provenance defect, not evidence that existing `.12` was built dirty or contains unexpected code. The current checkout has unrelated changes, including the parent-owned loader, which makes this a concrete release-process concern.

Reproduction by code proof (no build run): modify any included source without committing, then invoke the recipe; it copies that modified file while manifest.pluginCommit remains the unchanged HEAD. Priority P2 because reviewers cannot reconstruct the input identity from the claimed commit alone; source.tar mitigates source availability but is not itself hashed in this manifest. No runtime exploit or observed failed release is claimed.

Minimal fix: have the parent build only from a frozen snapshot of the intended committed inputs; fail on tracked modifications and relevant untracked source files, or explicitly attest a dirty snapshot with its digest. Read all build inputs/recipe from that snapshot. Record its full commit and digest. For `.13`, the authorized parent sequence (commit first, freeze inputs, build afterward) is a process mitigation; this auditor makes no code changes.
