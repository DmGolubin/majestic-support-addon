## UX06-01 — P2: deleted folder remains an invisible active filter and contaminates new drafts

**Impact / priority rationale:** routine folder deletion or a same-account catalog refresh can make existing templates disappear while the control says “Все папки”. Creating a template immediately afterward displays “Без папки” but retains the deleted folder ID, causing local validation failure. Recoverable by explicitly reselecting an option or remounting the editor; no data loss established. P2 because it obstructs normal browsing and saving, rather than being a visual preference.

**Evidence:**

- `src/vencord/ui/PanelPersonalLibrary.tsx:71` retains `folder` in local state without reconciling it against refreshed folder records.
- `PanelPersonalLibrary.tsx:115-116` copies that value into a new draft's `folderId`; `:177-178` continues filtering rows by that ID.
- `PanelPersonalLibrary.tsx:244-248` removes the vanished folder from the option list and reports “Шаблоны не найдены”.
- `src/vencord/ui/Select.tsx:27` maps an unmatched controlled value to option index zero; `:74` displays the first option without changing the controlled value. Thus the label and effective filter disagree. The editor folder dropdown behaves the same way at `PanelPersonalLibrary.tsx:207-209`.
- `src/vencord/ui/panel.ts:465-467` rejects a nonempty `folderId` missing from the catalog with `invalid_request`; `:422` translates this to a generic request to check title/text/command/project/folder.

**Executed reproduction:** `tests/masterUx.test.ts:132` selects the RO folder containing a valid RO template, opens that folder, confirms deletion, and supplies the successful refreshed catalog with the template moved to no folder. Actual `PanelPersonalLibrary` and actual `Select` render “Все папки” plus no cards despite one surviving record. Reselecting the already displayed “Все папки” restores the card. `tests/masterUx.test.ts:155` refreshes away the selected folder, creates a new template, and captures the stale ID in the request although the actual dropdown displays “Без папки”. The mutation adapter is mocked; local rejection is source-proven above, not an observed HTTP response.

**Minimal fix:** derive a valid effective list filter (`all` when its folder no longer exists) and use it consistently for filtering, the selector, and new-draft initialization. Handle missing folder values in existing editable drafts explicitly as well; do not alter a frozen pending mutation body or idempotency key. Avoid silently rendering the first option for unmatched values without reconciling or identifying the missing selection.

**Acceptance:** after local or remote folder removal, surviving templates are visible under the displayed filter; new drafts use `folderId: null`. An already open draft whose folder disappears needs an explicit valid selection or clear missing-folder message. Parent visual scenario A below.

## UX06-02 — P2: field-entry dialog lacks input names and selected-option semantics

**Impact / priority rationale:** a person using assistive technology cannot reliably identify which template field an input edits or which predefined answer is selected. This affects the dialog immediately before insertion. P2 for a functional accessibility barrier; no screen-reader session was performed. Deduplicate with the accessibility role if independently reported there.

**Evidence:** `src/vencord/ui/Dialogs.tsx:59-67` renders a sibling `<label>` without `htmlFor`, and a text input without `id`, `aria-label`, or `aria-labelledby`. Choice buttons at `:62` expose selection only through the CSS class `on`, with no `aria-pressed`, `aria-checked` or selection role. Frame at `:26-30` also lacks dialog naming/modal semantics, though focus trapping is provided separately by `index.tsx:70-110`; this is not a missing-focus-trap finding.

**Executed proof:** `tests/masterUx.test.ts:208` executes actual `Dialogs`, `Fields`, and `Frame` with a text field and a selected predefined option. It verifies that there is no associated text-input label and no exposed pressed/checked state. This is element-tree evidence; browser accessibility-tree output and actual spoken announcements remain unverified.

**Minimal fix:** associate each input with a unique label ID (or wrap it with its label), group choices by field name, and expose their selected state (`aria-pressed` is a minimal fit for existing toggle buttons). Add appropriate named dialog semantics to Frame without removing the existing keyboard trap.

**Acceptance:** the parent harness accessibility tree exposes the field name and selected value, and a keyboard/screen-reader check can distinguish two text fields and two choice groups. Parent scenario B below.

## UX06-03 — P3: token builder processes IME Enter with keyCode 229 as Add

**Impact / priority rationale:** in an input event carrying `keyCode: 229` with `isComposing: false`, the field builder inserts a token and closes while text composition is still being handled. The narrower event condition and lack of a real IME reproduction limit this to P3. This is a concrete inconsistent guard, not a claim about its frequency on the user's machine.

**Evidence:** `src/vencord/ui/TokenToolbar.tsx:32` checks only `nativeEvent.isComposing` before submitting Enter. The corresponding field-entry handler in `Dialogs.tsx:67` and dropdown handler in `Select.tsx:61` also reject `keyCode === 229`. The token builder's `:18-23` inserts and closes the disclosure on successful submission.

**Executed reproduction:** `tests/masterUx.test.ts:191` opens the actual TokenToolbar, enters a valid field name, and invokes its actual key handler with `key: Enter`, `keyCode: 229`, `nativeEvent.isComposing: false`. The insertion callback receives `{{ник}}`, default handling is prevented, and the builder closes. Synthetic event/code proof only; no claim of live OS IME reproduction.

**Minimal fix:** use the same composition guard as the other controls (`isComposing || keyCode === 229`) before submitting. Keep ordinary Enter submission working.

**Acceptance:** both composition forms leave the builder open and do not insert; ordinary Enter inserts exactly once. Parent scenario C below.
