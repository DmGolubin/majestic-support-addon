## M09-01 — P2: category discovery does quadratic work during every query recalculation

Evidence: `src/core/rank.ts:72-75`, specifically `out.includes(t.category)` for every template. With n distinct categories this performs n(n-1)/2 previous-category comparisons. `src/vencord/ui/Window.tsx:153-158` invokes it synchronously before filtering/search, inside a memo whose dependencies include query (`:179`). Snapshot accepts 10,000 FAQ entries (`src/core/panelCatalog.ts:85`, `:245`) with individual category strings (`:267`); the synthetic catalog in the test successfully validates before category discovery.

Reproduction: run `node node_modules/vitest/vitest.mjs run tests/masterPerformance.test.ts --silent=false --reporter=verbose`. First test generates 100 / 1,000 / 10,000 FAQ entries, each with a distinct `Category i`, and calls the actual parser and `categoriesOf`. Category discovery measured 0.144 / 2.642 / 2296.364 ms in the recorded run. Times include the length assertion; the quadratic code proof does not depend on machine timing. No arbitrary timing assertion or pass/fail performance threshold is used.

Impact and priority: a valid high-cardinality catalog can impose substantial synchronous work whenever search text changes, even when no results match. P2 because the accepted maximum-size synthetic input demonstrates multi-second computation on this machine, but actual account category counts and Discord interaction latency were not measured. This is not evidence that ordinary small catalogs are slow.

Minimal proposed fix (not applied; production read-only): track seen categories with a Set while appending first occurrences to the output array, preserving first-seen order and omission of null/empty categories. Validate duplicate/null/empty category behavior and rerun this bounded workload. Caching categories by catalog revision could additionally avoid repeated work, but is not necessary to remove the quadratic algorithm. Parent coordinates any Window/UI changes.

Duplication: no matching category-discovery finding was found in the available master reports searched at audit time. Agent04's M04-02 concerns malformed-brace normalization, a different algorithm/path.
