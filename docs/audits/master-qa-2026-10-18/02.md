## 2. Confirmed integration gaps and priority rationale

These are planning dependencies for X01/I02/I05, **not newly discovered production regressions**. P2 means required work before claiming BD support, not a reason to block the present Vencord-based renderer release. Security and insertion gates below would block a future BD release if unresolved.

### R02-01 · P2 · Shared UI/application boundary is incomplete

**Code proof:** `platform.ts` imports Vencord storage, insertion and Discord stores (`src/vencord/platform.ts:7–16`). UI imports are also distributed outside this file: `Host.tsx:7–8` requires Vencord ErrorBoundary/hooks; `ui/observable.ts:7` requires host hooks; `ui/panel.ts:7` needs UserStore/FluxDispatcher; `ui/ticketSound.ts:7` needs channel stores/dispatcher. `index.tsx:9–12` owns settings, chat buttons and root creation. Merely replacing `platform.ts`, or renaming a renderer bundle to `.plugin.js`, leaves these dependencies unresolved.

**Reproduce by inspection:** inventory imports with `rg -n '^import' src/vencord`; follow `scripts/sync-vencord.mjs:11–15` and `standalone/build.mjs:28–30`. Both distributions currently satisfy those imports through Vencord.

**Minimal future change:** introduce explicit host services for UI/runtime, lifecycle, Discord context, settings and clipboard; first have Vencord implement them without changing product behavior. Move shared UI and application orchestration behind those services, then add a BD shell. Reuse existing core algorithms and `StorageLike` (`src/core/state.ts:15–18`) rather than porting the 0.5.1 application. Parent must finish/reconcile Q09 and UI-state changes before extraction.

**Limit:** no module resolution, compilation or BD launch was attempted. The source-level dependency is confirmed; any exact runtime failure message is untested.

### R02-02 · P2 · Panel permission and persistent-session bridges are host-specific

**Code proof:** with `IS_WEB` absent/false and no `VencordNative.csp`, `ensurePanelPermission()` returns `unavailable` (`src/vencord/panelPermission.ts:32–36`). `beginPanel()` exits on that result before creating its vault (`src/vencord/ui/panel.ts:352–362`). Thus substituting UI and Discord stores alone cannot make current panel login work in a BD-only environment.

Separately, the vault factory requires `VencordNative.pluginHelpers.SupportTemplates` and returns `undefined` without it (`src/vencord/panelVault.ts:26–43`). This is deliberate memory-only capability, not a proven token leak. Native persistence uses Electron `safeStorage`, validated sender/profile and process ownership (`src/vencord/native.ts:33–68`). The core vault contract requires atomic replacement and resolution after durable storage (`src/core/panelClient.ts:57–61`).

**Minimal future change:** inject a host permission/network capability and a separate optional protected vault. Preserve memory-only behavior if a BD secure-storage implementation has not been verified; disclose the lost restart persistence and do not claim persistence parity. Never map the vault to ordinary BD settings storage. Validate account/profile/origin isolation, refresh rotation, atomic writes and concurrent ownership before enabling persistent credentials. Existing `tests/panelPermission.test.ts:7–43` and `tests/panelVault.test.ts:353–382` illustrate mocked host boundaries; they are not BD tests.

**Priority rationale:** this prevents feature parity on the planned adapter. There is no evidence that current Vencord persistence is broken by this dependency, or that secrets were exposed. Availability of a safe BD-native bridge remains an open design question, not an asserted API capability.

### R02-03 · P2 · Transport compatibility requires a separate proof

**Code proof:** the common JSON transport accepts an injected fetch but relies on abort signals, redirect rejection, response headers and a cancellable streaming body (`src/core/panelTransport.ts:47`, `:71–145`). SSE requires those properties and incremental `body.getReader()` processing (`src/core/panelEvents.ts:101–175`). The public BD API documents `Net.fetch` returning `HydratingResponse`; the method's name alone does not prove it satisfies this exact contract. [Official Net API](https://docs.betterdiscord.app/api/Net).

**Minimal future change:** select and test a BD transport against the existing contract, preserving the fixed origin, omitted credentials, redirect refusal, bounded body parsing, sanitized errors, abort, Retry-After and incremental SSE. If an adapter wrapper is necessary, keep it behind the existing transport/event interfaces. Do not simply cast a BD response to browser `Response`, bypass permission handling, buffer an indefinite SSE stream or silently weaken freshness/revocation handling.

**Priority rationale/limit:** mandatory parity work before BD acceptance, not evidence that BD networking is defective. No BD request or production endpoint was called; actual response behavior, CSP/CORS and streaming capability remain unverified.

## 3. Historical insertion code: exclusion from the new adapter

`reference/bd-0.5.1/SupportTemplates.plugin.js:1298–1318` enumerates every module matching `dispatchToLastSubscribed` and dispatches INSERT_TEXT to each. A returned array with two matching modules therefore produces two calls by direct control-flow proof. Lines 1321–1343 then try `execCommand` and synthetic paste if a delayed text probe does not detect insertion; lines 1290–1293 define that heuristic.

This is a **historical migration hazard, not an active current-adapter defect**. Actual duplicate visible text, delayed Slate behavior and multiple matching modules in current Discord were not reproduced. Do not assign it a current production incident severity or edit the historical file in this audit.

Minimal future prevention: use one validated insertion capability for a captured editor/channel/generation, preserve cancellation and freshness checks, and do not fan out insertion attempts. Existing current code captures the target (`src/vencord/ui/op.ts:7–40`), validates the operation (`ui/flow.ts:25–46`) and calls the platform insertion once (`ui/flow.ts:243–245`). The Vencord primitive itself is in `platform.ts:18–35`; selecting a BD equivalent needs a dedicated probe. A clipboard fallback must accurately report whether copying succeeded. No send-message or ticket-claim primitive belongs in this adapter.

2. Exercise the shared application against synthetic host services. Validate unavailable capabilities, failed storage, account changes, channel/editor replacement, late completions after stop and double activation.
3. Create a BD shell/build target only in a separately authorized implementation phase. Validate current module shapes and network/secure-storage capabilities in an isolated supported host. The old 0.5.1 file remains reference material.
4. Test the packaged artifact independently, record BD/Discord/OS/plugin versions, then consider I05 acceptance. Acceptance of `.12` in the Vencord-based host cannot substitute for this matrix.

Future acceptance must cover enable/disable/reload without duplicates, main chat and side thread/editor selection, allowed guilds and disabled DMs/other guilds, Ctrl+Alt+T/inline/IME/Shift, insertion cancellation after channel/account/freshness changes, no automatic send/claim, protected-session availability and rotation, SSE reconnect/revocation, reminders/audio cleanup, settings persistence failure, conflicting old plugins and clean uninstall.
