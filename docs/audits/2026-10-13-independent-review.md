## Оставшиеся проблемы

### R1 · P1 · Контекстное меню остаётся невидимым, но принимает Enter

Код: [ContextMenu.tsx:84](../../src/vencord/ui/ContextMenu.tsx#L84), [ContextMenu.tsx:87](../../src/vencord/ui/ContextMenu.tsx#L87), [ContextMenu.tsx:144](../../src/vencord/ui/ContextMenu.tsx#L144).

На изменение `menu` layout-effect измеряет элемент и записывает `pos`. Обычный effect, зависящий от того же `menu`, затем выполняет `setPos(null)`. Зависимости измерения больше не меняются. Итоговый элемент остаётся с `visibility: hidden`.

Подтверждено **на настоящем компоненте ContextMenu с React 19.1.0 в headless Chrome**, а не имитацией порядка hooks:

- открытие меню для B;
- через 100 мс: четыре кнопки в DOM, `visibility = hidden`;
- Enter вызывает `insertTemplate(B)` в адаптере вставки.

То есть пользователь не видит меню и выбранный пункт, но клавиатура уже выполняет его действия. Подобный тест отсутствует среди 108 тестов ядра.

Исправление: объединить сброс и измерение позиции в одном layout-effect либо изменить модель состояния так, чтобы поздний эффект не стирал результат измерения. Добавить тест с реальным React на открытие, закрытие и повторное открытие меню. До исправления не считать пункты 3 и 16 аудита закрытыми.

### R2 · P1 · Захват редактора при открытии мышью выполняется слишком поздно

Код: [index.tsx:55](../../src/vencord/index.tsx#L55), [index.tsx:38](../../src/vencord/index.tsx#L38), [op.ts:27](../../src/vencord/ui/op.ts#L27), [platform.ts:59](../../src/vencord/platform.ts#L59).

`captureWindowTarget()` вызывается из `onClick`. Перед click браузер уже переводит фокус на кнопку. `activeEditor()` при фокусе вне Slate возвращает первый редактор — основной чат. Новый контекст надёжно хранит этот уже неверный результат.

Браузерный сценарий с двумя редакторами и фокусируемой кнопкой:

- фокус в `thread`;
- обычный click по открывающей кнопке;
- на момент захвата `document.activeElement = opener`, сохранённый редактор = `main`;
- захват до потери фокуса сохраняет `thread` корректно.

Стенд воспроизводит браузерную последовательность фокуса и настоящие `captureWindowTarget`/`activeEditor`. В Vencord ChatBarButton передаёт onClick в Clickable; обработчика захвата цели до переноса фокуса в коде плагина нет. Само поведение Clickable и реальную маршрутизацию Discord INSERT_TEXT всё ещё нужно проверить в Discord. Ранее присланные пользователем логи также показывали фокус на `div.button.button` перед click и открытием окна.

Исправление: фиксировать цель на pointer/mousedown до default focus либо хранить последнего действительно активного редактора с привязкой к каналу. Не перезаписывать этот снимок в последующем onClick. Отдельно проверить выделение текста и редактирование сообщения; сохранение DOM-элемента само по себе не доказывает адресную работу `dispatchToLastSubscribed`.

### R3 · P2 · Импорт не отменяет вставку, уже ожидающую буфер обмена

Код: [Settings.tsx:30](../../src/vencord/ui/Settings.tsx#L30), [flow.ts:30](../../src/vencord/ui/flow.ts#L30), [flow.ts:196](../../src/vencord/ui/flow.ts#L196).

Очистка меню, compose и диалогов сделана. Но ни revision набора шаблонов, ни generation операции при импорте не меняются. `supersede()` отменяет только текущий диалог. Если его уже нет, существующая операция сохраняет старый объект шаблона.

Воспроизведение на исходных Store/flow/op с управляемым Promise чтения clipboard:

1. Начать вставку `OLD {{clipboard}}`.
2. Пока readClipboard ожидает, импортировать набор с шаблоном `New`.
3. Выполнить точную последовательность очистки из Settings: `supersede`, очистка confirmedForeign и ui.
4. Завершить чтение clipboard значением `CLIP`.
5. Вставка получила **`OLD CLIP`**, хотя актуальный набор уже содержит `New`.

Исправление: отдельная ревизия данных/отмена операций при успешной замене набора, проверяемая после каждого await и непосредственно перед вставкой. Не обязательно смешивать ревизию данных с поколением запуска плагина. Пункт 9 закрыт частично.

### R4 · P2 · ResizeObserver не отслеживает перемещение без изменения размеров

Код: [uiState.ts:95](../../src/vencord/ui/uiState.ts#L95).

Наблюдается размер одного chatArea, плюс resize окна. Положение элемента может измениться без изменения его ширины и высоты: например, при изменении соседних/родительских областей. В таком случае обновление геометрии не запланировано. Повторный поиск заменённого элемента также выполняется только при уже пришедшем сигнале, а не обнаруживает замену самостоятельно.

Проверено в Chrome с настоящей `watchChatArea` и настоящим ResizeObserver: chatArea перемещён с y=600 на y=550 при неизменном размере; число callback осталось 1 → 1 (только первоначальное уведомление). Поэтому утверждение «следит за всеми перемещениями» неверно. Рост самого редактора обработан, все виды перестроения Discord — нет.

Исправление: определить дополнительные сигналы изменения layout/редактора, наблюдать подходящие контейнеры и обновлять назначение при его замене. Оставить объединение через rAF и не возвращать постоянные измерения на каждом hover. Пункт 17 остаётся частичным; конкретные reply/thread сценарии нужны в Discord.
