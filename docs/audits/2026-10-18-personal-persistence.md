# A15: сохранение личных шаблонов при ошибке записи

## Воспроизведение

В `Store.savePersonal` и операциях папок общая память менялась раньше завершения `storage.set`. Отклонённый черновик был доступен поиску/вставке; последующая запись настроек могла сохранить его, несмотря на отмену в редакторе. Удаление при отказе записи аналогично убирало шаблон и его избранное/бинд из памяти.

Девять новых регрессионных сценариев упали на исходной реализации: создание, редактирование, удаление, три операции папок, параллельные настройки при успешной/неуспешной записи, конфликт команд после отказа первого создания. Это локальное воспроизведение с управляемым отказом StorageLike; настоящий диск и данные пользователя не повреждались.

## Изменение хранилища

- Личные записи и папки используют общую очередь с остальными сохранениями. Валидация выполняется в очереди, после предыдущих операций.
- До успешного завершения записи остаётся опубликована прежняя библиотека. Отказ не меняет каталог, версию набора и ссылки на шаблон.
- Черновик захватывается при нажатии сохранения. Его дальнейшее изменение не влияет на поставленную в очередь операцию.
- После успешной записи публикуется только изменение каталога и относящихся к удалению ссылок, сохраняя изменения настроек, сделанные во время ожидания.
- Следующие локальные записи получают актуальный подтверждённый каталог при исполнении очереди; старый снимок настроек не возвращает удалённые записи.
- Библиотека панели сохраняет прежнее поведение снимков предпочтений: они захватываются заранее, чтобы очистка каталога при выходе не уничтожила уже поставленное сохранение. Сетевой CRUD этим исправлением не добавлен.

В адаптере Vencord `DataStore.set` ждёт завершения IndexedDB-транзакции, а не только отправки запроса записи (`src/api/DataStore/index.ts` в установленной основе). Store полагается на этот контракт. Это не гарантия работы при повреждении диска или согласования между независимыми процессами.

## Проверка

Сценарии дополнены параллельным успешным созданием с одинаковой командой, изменением ссылок во время удаления, импортом FAQ во время сохранения, фиксацией черновика при вызове и переименованием папки перед созданием шаблона.

Независимое ревью обнаружило два пограничных случая новой очереди. Оба воспроизведены падающими регрессионными тестами и исправлены:

- Сброс демосессии теперь создаёт отдельное хранилище. Завершение прежней записи не возвращает личный шаблон или папку в новую сессию.
- Импорт из настроек ждёт завершения очереди записей перед проверкой конфликтов биндов. Клавиша, освобождённая ожидающим удалением личного шаблона, доступна импортируемому FAQ. Синхронный импорт при ожидающих личных операциях отклоняется с понятной ошибкой; для UI используется `importTextAsync`.

Повторное ревью выявило обратный порядок двух импортов при промежуточной записи настройки. Отдельная очередь импорта теперь резервирует порядок при вызове и продолжает работу после ошибки предыдущего файла. Регрессия воспроизведена до исправления. Итоговое независимое ревью: блокирующих замечаний в проверенном изменении нет.

Изменение импорта здесь касается порядка операций. Откат самого импорта при ошибке записи этим блоком не добавлен.

## Редактор

- Повторное нажатие сохранения блокируется сразу, до следующего рендера.
- Пока идёт запись, недоступны отмена, смена вкладки, закрытие окна, Escape и ранее открытое подтверждение закрытия.
- Ошибка оставляет черновик и возможность повторить сохранение. Отмена после ошибки не публикует отвергнутый текст.
- Копия считается несохранённым черновиком сразу. Редактирование удалённой записи не превращается в её повторное создание.
- Редактор привязан к выбранному экземпляру библиотеки и поколению переключения. Завершение старой операции после размонтирования или перехода A → B → A не закрывает новый редактор и не сбрасывает его признак сохранения.
- Импорт захватывает выбранную библиотеку до чтения файла; смена библиотеки не перенаправляет старый импорт в новый аккаунт.
