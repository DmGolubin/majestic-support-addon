# BetterDiscord .19: память, простой и повторное открытие окон

Дата: 19 октября 2026. Проверяется опубликованный `SupportTemplates.plugin.js` версии `1.0.1-canary.19`, source `7430ecfcf1b462ddb87bdc8cb41d3c1d55afb35b`, SHA-256 `81aa43daf7ca921ec7acda404eedf08a107416a2507200fecbe6111caf355155`.

## Методика

Два независимых источника измерений:

1. Read-only выборка восьми процессов запущенного Discord Canary: 60 точек, 591,5 секунды между первой и последней. Пользовательский клиент не перезапускался и не изменялся. Это наблюдение всего клиента при текущем использовании, а не контролируемый простой отдельного плагина.
2. Изолированный Chromium headless с точным опубликованным BetterDiscord bundle, React production и реальными UI/lifecycle/panel client/SSE parser. Подменены только API, Discord stores/event bus и недоступные native host-возможности. Каталог: 134 тестовых FAQ и один личный шаблон; реальные аккаунты, сообщения и токены не используются. Исходный CommonJS bundle исполняется в CommonJS-области; тестовые hooks доступны отдельно.

После прогрева — 500 циклов: список → настройки → три вкладки → личный редактор → отмена → закрытие. Это 1 000 открытий двух основных окон, плюс 20 прогревочных циклов. Затем по 180 секунд простоя с закрытыми окнами, открытым списком и открытыми настройками. Отдельно — 30 stop/start и 100 монтирований native BD settings panel. Дополнительный прогон: 100 переключений подробной отладки и 60 секунд простоя с ней.

Перед каждой контрольной точкой выполняются две сборки мусора через CDP. JS heap, DOM nodes, event listeners, подписки host, таймеры, observers и запросы измеряются независимо. Инструментация не хранит сильных ссылок на DOM или callbacks. `TaskDuration` измеряет занятость основного потока тестовой страницы; время принудительной GC между точками исключено. Это не процент CPU всего Electron и не полный размер памяти плагина: CSS, DOM, GPU, код движка и native-хост не равны JS heap.

Контроль без плагина: React + mock host, 60 секунд, 4,674 мс TaskDuration. Данные стенда и выводы ограничены фактически измеренным интервалом; многосуточный режим, native updater/vault/audio, настоящий Discord React и реальная сеть отдельно не профилировались.

## Штатные сценарии: результаты

Полный основной прогон занял **693,73 секунды (11 минут 34 секунды)**, без page errors. Это короткий soak с большим числом действий, не проверка многосуточной работы.

После 20 прогревочных циклов JS heap составлял 4,200 МиБ, после следующих 500 — 4,789 МиБ. Во всех контрольных точках после закрытия окон сохранялись **129 DOM nodes и 324 JS event listeners**: накопления этих ресурсов от открытия окон не обнаружено. Небольшой рост heap наблюдался; отсутствие всех удержаний памяти из этого не следует.

| Состояние | Измерено | Занятость основного потока стенда | JS heap после GC, начало → конец |
| --- | --- | --- | --- |
| Окна закрыты | 180 с | 0,021% | 4,792 → 4,856 МиБ |
| Список открыт | 180 с | 0,099% | 5,165 → 5,920 МиБ |
| Настройки открыты | 180 с | 0,019% | 5,130 → 5,872 МиБ |

Во всех трёх состояниях число DOM nodes/listeners оставалось постоянным; mutation/animation callbacks за время неподвижного простоя — ноль. В открытых окнах heap вырос при обновлениях каталога, затем вышел на плато в пределах короткого наблюдения. Проверка API продолжалась примерно раз в минуту; SSE-соединение оставалось одно. Его heartbeat каждые 15 секунд создаёт **тестовый сервер**, не отдельный production-таймер плагина. Открытый список дополнительно проверяет геометрию каждые 250 мс.

После штатного stop: таймеры, pending RAF, Flux/store/settings подписки и SSE — ноль. Счётчик MutationObserver показывал один остаточный observer: отдельная проверка со стеками создания и WeakRef установила, что он принадлежит **Playwright InjectedScript**; observer `mountChatButtons` уже собран GC. Не следует считать этот остаток утечкой плагина.

При этом CDP после stop продолжал видеть 533 DOM nodes / 233 listeners при 13 живых HTML-элементах. Это удержанные отсоединённые объекты, а не полностью освобождённый UI. После 10/20/30 повторных start/stop и 100 монтирований BD settings их количество оставалось тем же; heap после stop вырос с 4,107 до 4,361 МиБ. Признаков линейного накопления на этих повторах нет; точные владельцы всего остаточного DOM heap snapshot-ом не атрибутированы.

Отладка: 100 включений/выключений без роста числа DOM nodes/listeners, 60 секунд подробной отладки — 74,825 мс TaskDuration (около 0,125% основного потока), после stop таймеры и observers этого прогона обнулены. Ротация OAuth-токена не покрыта: тест завершился раньше срока 900 секунд.

Машиночитаемые результаты: [агрегированная сводка](2026-10-19-memory-idle-results.json). Для длительной эксплуатации остаётся отдельная проверка на несколько часов в настоящем BetterDiscord, включая смену каналов, переподключение сети и ротацию токена.

## Живой Canary

Все восемь PID сохранялись в течение выборки. Суммарная private-память: **1 313,13 → 1 212,07 МиБ**, диапазон **1 198,36–1 332,02 МиБ**. Суммарное CPU-время выросло на 33,59 с за 591,54 с: **5,68% одного логического процессора**, или **0,237% общей мощности 24 логических процессоров**.

Сумма handles выросла с 6 017 до 6 129. Сам по себе этот показатель не доказывает утечку: без атрибуции к типам handle и функциям клиента нельзя приписывать рост плагину. В данной выборке роста общей private-памяти не обнаружено; это не доказательство отсутствия всех утечек.

## Подтверждённые дефекты .19

### 1. Неотменённый частичный запуск chat buttons

В `betterdiscord/chatMounts.ts` observer подключается до подписки/первого scan, а cleanup возвращается только в конце. При исключении после подключения ресурсы недоступны `entry.offButtons`.

Воспроизведение: исключение на второй `CHANNEL_SELECT`-подписке в каждом запуске (после регистрации callback), 10 повторов. После завершения осталось **10 MutationObserver и 10 Flux-подписок**, хотя корней плагина уже нет. Это линейное накопление именно при аварийном запуске. В штатных циклах этот отказ не имитируется.

### 2. Исключение unsubscribe прерывает stop

В `src/vencord/ui/panel.ts` cleanup выполняет последовательные unsubscribe без изоляции ошибок. Исключение до удаления `LOGOUT` прерывает `upstream.stop()` в `src/vencord/index.tsx`; BD runtime уже помечен неактивным.

После одного внедрённого отказа остаются **корень UI, четыре Flux-подписки и один store listener**. Повторный stop их не убирает. Это подтверждённый аварийный путь, а не наблюдавшийся сбой пользовательского Canary.

### 3. Ограниченное удержание закрытого состояния

После поиска `fixture`, закрытия окна/очистки compose и удаления тестового composer обе сохранённые цели указывают на отсоединённый редактор. Stop обнуляет цели. `visibleItems` после поиска сохраняет **70 результатов**, включая после stop. Это удержание последних целей/последнего набора, не доказанное накопление всех открытий. Причины: сильные ссылки в `ui/op.ts` и экспортируемый массив в `ui/Window.tsx`.

### 4. Фоновая работа на чужие DOM-изменения

При закрытых окнах 120 изменений отдельного участка страницы вызвали **121 дополнительный animation callback** через общий observer chat buttons. Во время неподвижного простоя этот механизм не вызывался. Это потенциальный источник лишней работы в активном Discord; само по себе не утечка.

Исходники production и установленный плагин в рамках этой проверки не менялись. Найденные дефекты остаются в .19; результаты проверки не следует представлять как выпуск исправления.

## Воспроизведение

Из корня репозитория:

```powershell
node scripts/qa/prepare-memory-harness.mjs
python scripts/qa/memory-soak.py
```

Пока основной прогон держит локальный сервер, независимые проверки запускаются командами `python scripts/qa/memory-faults.py`, `python scripts/qa/memory-control.py` и `python scripts/qa/memory-debug.py`. Наблюдение живого клиента: `powershell -NoProfile -File scripts/qa/sample-canary.ps1`. Сводка: `node scripts/qa/summarize-memory.mjs`. Все промежуточные данные находятся в игнорируемом `artifacts/memory19/`; опубликованная сводка содержит только агрегаты реального процесса и синтетические данные стенда.

Для запуска нужны Python Playwright/Chromium и установленные зависимости `betterdiscord/`. Локальный HTTP-сервер закрывается вместе с Python context manager. Штатный skill-helper на Windows оставлял дочерний сервер после остановки shell; две проверенные тестовые копии были остановлены, после чего использован сервер внутри процесса теста.
