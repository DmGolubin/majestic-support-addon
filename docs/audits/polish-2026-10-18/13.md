## Verified findings

### 13-1 — P2: Unsaved command prefix is silently discarded on closing settings

- **Location:** `src/vencord/ui/Settings.tsx:76` (prefix change), `Settings.tsx:60` (only personal editor reports dirty); dismissal at `src/vencord/ui/Management.tsx:19`.
- **Trigger:** Open Settings → Настройки with panel ready; change command prefix from `;` to `!` without pressing Сохранить; close via Escape, close button or backdrop; reopen.
- **Consequence:** New prefix is lost without the existing unsaved-changes confirmation. Prefix lives only in Settings state, is persisted only on form submit, and never contributes to the parent's dirty flag. Reopening initializes from the old stored prefix.
- **Minimal fix:** Include `prefix !== store.data.prefix` in the dirty value reported to Management, combined with personal-editor dirty state. Update the reported value after prefix edits and successful save. Ensure cancelling a close preserves the typed prefix and explicit discard permits closing.
- **Evidence:** An isolated Node/TypeScript VM harness executed actual Settings.tsx with state hooks and stubbed dependencies: opened general tab, invoked prefix input change, rerendered; rendered value became `!`, stored value remained `;`, and `onDirty` received zero calls. Management's actual close callback then has no reason to show confirmation. No test file was added.

### 13-2 — P2: Escape used during IME composition also dismisses the dialog

- **Location:** `src/vencord/ui/Dialogs.tsx:17`; same missing guard at `src/vencord/ui/Management.tsx:25`.
- **Trigger:** Start composing text using an IME in a template field; press Escape to cancel the composition/candidate selection. Event has `isComposing: true` (or the legacy `keyCode: 229` signal).
- **Consequence:** Frame consumes Escape and resolves the field dialog with null, discarding entered field values; Management closes when clean or opens its unsaved confirmation when dirty. The document capture listener acts before the input can handle the event. The field Enter handler already recognizes composition, but these Escape listeners do not.
- **Minimal fix:** Return from the Escape dismissal path while `e.isComposing || e.keyCode === 229`; apply consistently to both listeners. Preserve ordinary Escape behavior.
- **Evidence:** Isolated harness transpiled and executed actual Management and Frame effects. Dispatching Escape with both composition signals invoked `ui.set({ management: false })` for Management and called Frame's cancellation callback exactly once. Assertions passed. This is a synthetic event reproduction; physical IME/Discord acceptance was not performed.

### 13-3 — P2: Cancelling an insertion dialog leaves keyboard focus without a return target

- **Location:** `src/vencord/ui/Dialogs.tsx:22` (focus acquisition effect has no restoration cleanup). Relevant caller: `src/vencord/ui/flow.ts:214` returns on cancellation before `focusTarget` at line 215.
- **Trigger:** From the focused chat composer, invoke a template that needs field values or confirmation; cancel using Escape or Отмена. The template window is closed by insertTemplate before the dialog opens (`flow.ts:212`).
- **Consequence:** The focused input/button is removed with the dialog, with no explicit restoration to the still-connected composer. Keyboard-only users must locate/refocus the composer before continuing to type. Successful insertion restores the target, but the cancellation branch does not. The Window.tsx restoration effect helps only when that window remains mounted/open.
- **Minimal fix:** Capture the pre-dialog active element and restore it on cleanup when still connected and focus still belongs to the closing dialog/body. For insertion paths whose original control was already unmounted, restore the captured composer through the cancellation path, preserving the existing operation/context checks and avoiding focus theft when another dialog replaces it.
- **Evidence:** Isolated harness executed actual Frame effects with a connected previous focus target. Mount focused Frame; cancellation and unmount never invoked previous.focus (asserted zero calls). Source tracing confirmed the insertion cancellation return bypasses focusTarget. Native browser focus falling back after DOM removal was not exercised; no claim of live Discord validation.
