## Verified findings

### 05-1 — P2: FAQ mention protection changes link destinations

- Location: `src/core/panelCatalog.ts:191`; equivalent HTML path at `src/vencord/panelHtml.ts:42`.
- Trigger: valid FAQ text `[Help](https://example.org/@here/help) <https://example.org/@everyone>`. The `/` before `@` satisfies the mention boundary, even though these strings are URL components.
- Actual: both text and HTML snapshot paths produce `[Help](https://example.org/@\u200bhere/help) <https://example.org/@\u200beveryone>` (notation represents an actual U+200B character).
- Consequence: the stored template contains changed destinations; copying or inserting it no longer preserves the source URLs. Existing handle coverage only exercises `@support`, which never matches the affected alternatives.
- Minimal fix: preserve URL spans, including Markdown destinations and autolinks, while neutralizing actual mentions outside them. Apply the same treatment in both conversion paths.
- Test evidence: isolated Node reproducer imported the actual TypeScript modules through in-memory TypeScript transpilation, passed this input through `parseSnapshot` for each of `format: text` and `format: html`, and asserted exact equality to `input.replaceAll('@', '@\u200b')`. Both assertions passed. Add regression assertions that these URLs remain byte-for-byte unchanged while standalone `@here`/`@everyone` remain neutralized.

### 05-2 — P2: HTML attribute extraction takes href text from inside another attribute

- Location: `src/vencord/panelHtml.ts:45`, consumed at line 102.
- Trigger: `<a title="See href='https://wrong.example/'" href="https://right.example/">Help</a>`.
- Actual: `htmlToDiscordText` returns `Help <https://wrong.example/>` instead of the real href. The attribute regex begins matching at whitespace inside the quoted title value.
- Consequence: a valid legacy HTML FAQ silently acquires a different link destination. If the title contains `href='javascript:void(0)'`, the valid actual href is discarded and the output is just `Help`.
- Minimal fix: scan attributes while respecting quoted value boundaries, selecting only actual attribute names. Retain the existing URL protocol validation.
- Test evidence: isolated Node assertions against the actual converter confirmed both exact outputs above. No request was made to any example URL. Add cases for an href-like string inside title before the actual href, with both safe and rejected fake values.
