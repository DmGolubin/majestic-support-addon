## 01-1 — P2: a confirmed save can become a local validation failure after catalog refresh

- **Location:** `src/vencord/ui/panel.ts:473`, also `:453`; both call the full `guard()` whose folder validation is at `:434–436`. UI handling: `src/vencord/ui/PanelPersonalLibrary.tsx:156–160`.
- **Trigger:** create or update a template in folder F. The server successfully commits the mutation and returns its success record. Another panel client deletes F before the post-save snapshot is published (or an SSE-triggered reload publishes its removal before the mutation response is processed). Account, connection and scopes remain unchanged.
- **Observed behavior:** the post-response/post-refresh guard revalidates the original request's `folderId` against the newer catalog and throws local `invalid_request`. In the post-refresh case, `confirmed` is already true, but the action still rejects. Calling that same action again fails at its initial guard without another mutation. The UI classifies the first local `invalid_request` as definite rejection and drops the pending action, including its captured create UUID, while retaining the draft and showing an input-validation error instead of success.
- **Consequence:** a saved record is presented as an unsuccessful save. Retrying the unchanged draft is blocked by its obsolete folder ID. Clearing the folder and saving a create draft starts a fresh POST with a new UUID, despite the previous create having committed. Whether that second POST creates a duplicate or receives a name conflict depends on server validation; that downstream outcome was not tested.
- **Minimal fix:** separate account/session/permission fencing from mutable request validation. Preserve identity and permission checks after awaits, but only validate request fields before dispatch; do not revalidate the original folder/color against a newer catalog after receiving a valid success or after refreshing a confirmed mutation. Retain the confirmed result so recovery cannot generate a new create action merely because refresh changed request dependencies. Add a focused regression for both event orderings.
- **Evidence:** an isolated Node stdin reproducer transpiled and executed the actual `preparePanelWrite` function from `panel.ts` in a VM with mocked observables, transport, parsers and reload. Initial catalog contains F; the transport returns success once; either reload or the simulated concurrent catalog publication removes F. Assertions passed for both orderings: first action rejects `invalid_request`, second invocation rejects `invalid_request`, mutation count remains one. This is a deterministic controller reproduction, not a live HTTP/SSE test. UI consequences above are established by the cited catch branch.

```text
{"stage":"post-save-refresh","serverSuccess":true,"firstError":"invalid_request","retryError":"invalid_request","mutateCalls":1}
{"stage":"sse-before-response","serverSuccess":true,"firstError":"invalid_request","retryError":"invalid_request","mutateCalls":1}
```

Reproducer recipe: extract source between `export function preparePanelWrite(` and `export function openPanelPage(`; transpile with TypeScript CommonJS/ES2022; evaluate with `node:vm`. Supply a ready, fresh account A, generation 1, personal write scope, projects mj/ro, and folder `{id:"8",project:"mj"}`. Prepare POST `/personal-templates` with a fixed idempotency key and body `{title:"New",text:"Body",project:"majestic",folderId:"8"}`. Stub `mutate` to return a template record and `parsePersonalRecord` to return that record. For the first ordering, remove folder 8 inside the successful `loadLibrary`; for the second, remove it inside `mutate` before returning success. Invoke the prepared action twice and assert the output above. All mocks remain in memory; no reproducer file was created.

## Accepted fix — 2026-10-18

Implemented only in `src/vencord/ui/panel.ts` and `tests/panelIntegration.test.ts`, plus this report. The finding's line references above describe the reviewed pre-fix source.

- `guard()` retains account/client/epoch/generation, write-scope, shared-project and project-access checks before dispatch and after asynchronous work. Session revocation still cancels the action.
- `validateDraft()` checks mutable folder and palette dependencies before the first dispatch. After the dispatch guard passes, the action retains the original JSON, version and create UUID; uncertain retries let the server resolve that same operation even if its dependencies changed.
- The action captures the palette when dispatch first becomes possible, so a late valid response or idempotent replay is not rejected merely because SSE published a newer palette. Current project permissions and all record-shape validation still apply.
- Confirmed actions refresh without sending another mutation; post-response and post-refresh checks no longer revalidate obsolete draft dependencies.
- Added 10 regression cases: folder and palette changes independently in both response/SSE orderings; uncertain replay with identical JSON/UUID; first-dispatch validation for removed folder/color; confirmed and uncertain retry fences; scope revocation while awaiting a success response. Existing session-revocation and 412 tests remain enabled.

Validation: the initial new regression run reproduced three failures before the production fix. These are synthetic transport/SSE tests with real controller and catalog parsers; live panel behavior was not exercised. No roadmap changes, commits or graphify operations were performed.
