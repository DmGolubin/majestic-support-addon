# SupportTemplates — ТЗ на интеграцию с панелью

Дата: 16.10.2026. Редакция 1.1: продуктовые правила подключения, сроков, обновлений и отзыва согласованы владельцем. Технический контракт и реализацию подтверждает разработчик панели.

**Полный технический контракт:** [API v1: авторизация, данные, права, обновления и приёмка](PANEL-API-CONTRACT.md). Он уточняет предложения ниже; старый интервал обновления 15 минут отменён.

## 1. Цель и граница работ

Сайт — источник шаблонов и прав доступа. Плагин подключается к аккаунту панели, получает разрешённые данные и помогает использовать их в Discord. Пользователь разрабатывает плагин; разработчик панели реализует сервер, API и необходимые страницы сайта.

В целевой пользовательской сборке нельзя создавать параллельную библиотеку, не связанную с аккаунтом панели. Текущий импорт — временный способ тестирования прототипа. Его наличие не является требованием будущего продукта.

**Подтверждено пользователем 15.10:** личные шаблоны можно создавать, редактировать и раскрашивать прямо в плагине, как на сайте. Это одна библиотека аккаунта с двусторонней синхронизацией. Запрет отдельной локальной библиотеки не означает запрет редактора в плагине.

Ограничение локального интерфейса не защищает от модификации открытого исходного кода. Права на чтение и изменение серверных данных проверяет сервер; запрет независимого локального источника — поведение официальной сборки.

## 2. Текущее состояние, не путать с готовой интеграцией

Реализовано: локальное ядро, поиск и вставка, проекты, бинды, избранное, сборка ответа, диалоги, локальный импорт и диагностика.

Не реализовано: вход через панель, токен устройства, сетевой источник, синхронизация, права аккаунта, отзыв устройства.

По отдельному запросу пользователя 15.10 добавлен локальный прототип редактора: создание, изменение, копирование, удаление, цвета, папки, общий проект и команда. Личные записи хранятся отдельно от импортированных FAQ; импорт их не удаляет. Это временный режим до API, а не изменение требования об одной библиотеке аккаунта.

Настройки доступны из окна шаблонов по кнопке «Мои шаблоны и настройки» и из стандартных настроек плагина Vencord. Вкладка «Подключение» явно сообщает, что API ещё не подключён. Никакие запросы на запись на сайт не выполняются; перенос локальных записей в аккаунт предстоит согласовать и реализовать отдельно.

Закрытие живой приёмки 15.10 относится к существующему локальному прототипу. Оно не закрывает перечисленные продуктовые функции.

## 3. Кто что делает

| Область | Разработчик сайта | Разработчик плагина |
| --- | --- | --- |
| Аккаунт и доступ сотрудника | Использует существующую авторизацию панели, проверяет доступ | Отображает аккаунт и состояние подключения |
| Вход по коду | Запрос подключения, подтверждение/отказ, выдача токена устройства | Показывает код, открывает страницу подтверждения, опрашивает результат |
| Устройства | Список, срок действия и отзыв, проверка каждого запроса | Хранит токен, отключается при отзыве |
| FAQ | Выдаёт разрешённые проекты и стабильные идентификаторы | Кэширует, ищет, показывает и вставляет |
| Личные шаблоны | Редактор сайта, папки, CRUD API и права владельца | Редактор внутри плагина: создание, изменение, цвет, папка, команда, удаление и синхронизация |
| Синхронизация | Версии снимков, ошибки, удаление и изменение прав | Атомарно заменяет данные, показывает время и результат |
| Настройки | Выдаёт согласованную часть настроек аккаунта | Применяет их; хранит настройки устройства отдельно |

Плагин не отправляет сообщения и команды в Discord. Сохранение личного шаблона передаёт панели именно текст и метаданные, которые пользователь сохраняет в редакторе. Переписка Discord, значения полей при вставке, буфер обмена и статистика использования шаблонов автоматически на панель не отправляются.

## 4. Интерфейс плагина, который предстоит сделать

В локальном прототипе уже добавлена кнопка «Мои шаблоны и настройки» в окно шаблонов и сохранён вход через стандартные настройки Vencord. При подключении API сохранить оба входа и доступность на маленьком экране. Ниже описан целевой интерфейс, часть сетевых состояний ещё предстоит реализовать.

Разделы:

1. **Подключение:** «Подключить панель», код, срок ожидания, ссылка на подтверждение. После входа — имя аккаунта, доступные проекты, устройство, «Открыть панель», «Отключить».
2. **Синхронизация:** последняя успешная загрузка, число FAQ и личных шаблонов отдельно, состояние связи, «Обновить сейчас», понятная ошибка и повтор. Отображать возраст кэша.
3. **Шаблоны:** источник и проект, поиск, FAQ и «Мои». В «Мои» — папки, список и редактор: название, проект, команда, цвет, категории/теги (по согласованной схеме), текст с токенами; «Создать», «Сохранить», «Дублировать», «В корзину», «Открыть на сайте». FAQ здесь только для чтения; токен приложения не получает права редактировать FAQ даже у старшего сотрудника. Существующее окно вставки остаётся основным рабочим инструментом.
4. **Работа в Discord:** префикс, бинды, избранное, параметры превью, текущий выбор Tech. Для каждого параметра указать, хранится ли он на устройстве или в аккаунте.
5. **Диагностика:** версия плагина, версия схемы API, последняя ошибка синхронизации, копирование безопасного отчёта. Отладка выключена по умолчанию.

Состояния интерфейса: не подключён; ожидается подтверждение; подключён; обновление; сеть недоступна с кэшем; сеть недоступна без кэша; доступ отозван; требуется обновление плагина. Не показывать неработающую кнопку как готовую функцию.

Для редактора показывать состояния «Есть несохранённые изменения», «Сохраняется», «Синхронизировано», «Ожидает связи», «Конфликт», «Ошибка сохранения». Не закрывать изменённый редактор с потерей текста без выбора пользователя. Цвет должен сохраняться и одинаково отображаться на сайте и в плагине.

Без подключения не предлагать локальный импорт как обход. Первое подключение без сети не даёт библиотеку. Офлайн-работа после успешного входа зависит от согласованной политики доступа из раздела 7. Несинхронизированные правки относятся к конкретному аккаунту, а не образуют отдельный локальный источник.

## 5. Владение настройками — предложение к согласованию

| Данные | Источник / хранение | Запись из плагина |
| --- | --- | --- |
| FAQ, статус, категория, текст, цвет, команда | Сайт; локально только кэш | Нет |
| Личные шаблоны и папки | Общая библиотека аккаунта; локально кэш и очередь несинхронизированных правок | Да, через CRUD API с контролем версии |
| Доступные проекты и ограничения аккаунта | Сайт | Нет |
| Префикс | Предлагается настройка аккаунта, сайт → плагин | До согласования API — нет; не заводить две независимые истины |
| Избранное | В API v1 локально | Синхронизация — отдельное расширение контракта |
| Бинды, превью, выбор Tech, отладка | Предлагается локально на устройстве | Локально |
| Недавние и личная частота использования | Локально | На сайт не передаются |
| Собираемый ответ, поля, выделение, черновик | Только текущая локальная операция | На сайт не передаются |

Это предложение, а не уже согласованное требование синхронизировать все настройки. Разработчик панели должен подтвердить существующие настройки аккаунта и границу записи.

## 6. Предлагаемый контракт API

Ниже логический контракт. Пути, тела и сроки **не проверены на действующем сайте** и не объявляются существующими эндпоинтами. Разработчик панели может предложить эквивалентные пути и существующую схему.

### Вход без повторного Discord OAuth

1. Создать запрос подключения: клиент передаёт название плагина, версию и отображаемое имя устройства. Сервер возвращает короткий пользовательский код, отдельный секрет опроса, URL подтверждения, время истечения и интервал опроса.
2. Пользователь открывает страницу `/connect` в своём браузере и подтверждает устройство в уже авторизованном аккаунте панели.
3. Плагин опрашивает состояние по секрету опроса, а не только по короткому коду. Состояния: pending, approved, denied, expired.
4. При approved получает токен устройства и срок его действия. Код одноразовый; после отказа/истечения токен не выдаётся. При закрытии формы опрос прекращается.
5. Сервер ограничивает попытки и частоту опроса. Устройства видны и отзываются на сайте. Access token действует 15 минут; refresh ротируется, сессия истекает после 30 дней неактивности или 90 дней от разрешения. Перезапуск Discord восстанавливает безопасно сохранённую сессию и перепроверяет права; защищённое хранилище адаптера — условие выпуска.

Cookie браузера и Discord-токен не используются как постоянная авторизация плагина. Токен устройства не включается в отчёт, экспорт или репозиторий. Конкретное защищённое хранилище для Vencord и BD предстоит выбрать отдельно; обычный JSON/IndexedDB не считать защищённым хранилищем секретов.

### Чтение

- Информация о подключении: идентификатор аккаунта, отображаемое имя, разрешённые проекты, идентификатор устройства, срок доступа, поддерживаемая версия схемы.
- Снимок библиотеки: `schemaVersion`, непрозрачная `revision`, `serverTime`, `permissionsRevision`, списки FAQ, личных шаблонов и папок, согласованные настройки аккаунта.
- FAQ ru и ro запрашиваются независимо от выбранного региона браузерной сессии. Плагин сопоставляет ru → mj, ro → ro; EU не запрашивает.
- У каждого шаблона стабильный ID, версия записи, тип источника (FAQ/personal), непустой массив projects из mj/ro, название, текст, команда, категория/папка, теги, цвет, статус actual/needs_review/outdated, пояснение статуса, updatedAt и разрешённые действия. Общий шаблон имеет один ID и projects=[mj, ro]; null-проект является внутренним форматом прототипа, а не сетевым контрактом.
- Текст сохраняет токены и `[[greeting:end]]`; плагин не отправляет подставленные значения обратно.
- У папок стабильные ID и parentId, если поддерживается вложенность. У ссылок «открыть/редактировать на сайте» должен быть известный доверенный origin панели.
- Полный снимок включает все доступные записи: отсутствие прежнего ID означает удаление/утрату доступа. Если нужна пагинация, все страницы привязаны к одной revision и применяются только после полной загрузки.

Для первого выпуска достаточно полного снимка и проверки неизменившейся revision/ETag. Delta API не обязателен.

### Запись личных шаблонов и папок

Нужны операции создания, чтения, изменения, перемещения в папку, удаления в корзину и восстановления личных шаблонов; аналогичные операции папок. Цвет, команда, проект и текст входят в сохраняемые поля, а не только в настройки отображения на одном устройстве. Дублирование может быть обычным созданием с новым ID.

При создании клиент передаёт идентификатор операции для идемпотентного повтора: сетевой таймаут не должен создавать несколько копий. Сервер возвращает ID, версию и нормализованную запись. При изменении/удалении передаётся ожидаемая версия; если сайт уже изменил запись, сервер возвращает конфликт с актуальной версией. В редакторе сохранить обе версии и дать выбор «оставить мою», «взять с сайта», «сохранить копию». Старое предложение last-write-wins без явного разбора конфликта заменяется этим правилом.

Проверки владельца и прав выполняются на каждом запросе. Токен сотрудника не разрешает менять чужие личные шаблоны или FAQ. Схему лимитов длины текста, цветов, команд, папок/тегов и срока корзины согласовать с существующей панелью; возвращать ошибки конкретных полей.

Для избранного отдельно согласовать операцию с ID шаблона и ожидаемой версией. «Предложить правку» FAQ на первом этапе может открывать форму сайта без прямого изменения FAQ.

### Ошибки

Стабильный код ошибки, безопасное описание, requestId; для ограничения частоты — Retry-After. Различать: временную недоступность, неверный/истёкший токен, отозванное устройство, отсутствие прав на проект, несовместимую схему. Обычный 403 не интерпретировать автоматически как полный отзыв устройства без серверного кода причины.

## 7. Синхронизация и офлайн

- Согласовано: SSE-сигнал после изменения (ожидаемо 1–5 секунд, целевой p95 до 5 секунд), резервный условный запрос раз в 60 секунд и обязательная проверка перед вставкой при возрасте данных больше 30 секунд. Интервалы согласованы; при dirty или проверке старше 30 секунд вставка ждёт успешного ответа. Проверка каждой вставки не требуется. Детальный алгоритм, гонки, офлайн и исключения описаны в API-контракте v1. Одновременно не более одного запроса синхронизации; 429 учитывает Retry-After.
- Сначала проверить схему и весь ответ, затем заменить снимок атомарно. При повреждённом/неполном ответе сохранить последнюю исправную копию.
- Обновление библиотеки меняет поколение данных и отменяет ожидающие вставки, старые меню/формы/compose. Это использует уже существующую защиту версии набора в ядре.
- Удалённый шаблон исчезает из поиска; бинд на его ID не вызывает старую копию. Локальная статистика сама по себе не возвращает удалённые записи.
- Кэш и очередь записей привязаны к аккаунту и устройству. Выход/смена аккаунта отменяют операции; при несинхронизированных правках сначала показать предупреждение и выбор дождаться сохранения либо отказаться от них. Правки прежнего аккаунта никогда не отправляются под токеном другого.
- При временном отсутствии связи сохранять правки в ограниченную очередь аккаунта с идентификаторами операций и ожидаемыми версиями. После восстановления доступа повторить запись; конфликт требует решения пользователя. Не показывать «Синхронизировано» до подтверждения сервера. Срок/объём очереди и правила после отзыва согласовать вместе с офлайн-политикой.
- При явном отзыве отключить вставку и очистить токен/кэш. При простой сетевой ошибке не стирать исправный кэш.
- **Согласовано для FAQ:** после истечения 30-секундной свежести без успешной проверки вставка блокируется; кэш можно читать. Увольнение немедленно запрещает новые API-запросы всех устройств, даже с ещё действующим access token. Штатный клиент очищает кэш при обнаружении отзыва. Удаление уже скопированных текстов не является целью. Политика несохранённых личных черновиков уточняется отдельно.
- Серверные права пересекаются с локальной таблицей серверов: MJ, RO, Tech. Разрешение проекта в аккаунте не включает плагин на других серверах и в ЛС. Tech не даёт доступ к проекту, запрещённому аккаунту.

## 8. Переход с нынешнего прототипа

1. Согласовать контракт с разработчиком сайта и получить обезличенные примеры ответов/ошибок.
2. Реализовать состояния подключения и настроек в плагине на тестовом адаптере; явно обозначать тестовый режим.
3. Реализовать серверную часть, затем подключить реальные API и проверить права двумя тестовыми аккаунтами.
4. Перед переходом сохранить старые данные прототипа отдельно. Не загружать локальные шаблоны пользователя на сайт автоматически.
5. В пользовательской сборке убрать независимый импорт и локальный источник; включить редактор личных шаблонов аккаунта. Если миграция старых личных данных нужна, проводить её отдельной подтверждённой операцией, без скрытой автоматической загрузки.
6. Проверить вход, синхронизацию, отзыв, офлайн и обновление данных во время вставки. Только после этого объявлять версию с панелью готовой.

BD и Vencord используют единый контракт данных, но разные адаптеры UI/секретов. Помощник тикетов и статистика смены не входят в минимальный объём этого ТЗ. Статистика использования шаблонов на сервер не отправляется.

## 9. Приёмка интеграции

- Неавторизованный клиент не получает библиотеку; нельзя войти по одному угаданному короткому коду.
- Подтверждение, отказ и истечение кода работают; повторное использование завершённого запроса запрещено.
- Клиент видит только разрешённые проекты и доступные ему личные шаблоны.
- Создание, редактирование текста, команды, папки и цвета в плагине отражаются на сайте; изменения сайта возвращаются в плагин.
- Повтор запроса создания не создаёт дубликат. Одновременная правка сайта и плагина вызывает конфликт без молчаливой потери текста. Очередь одного аккаунта не уходит под другим аккаунтом.
- Изменение и удаление на сайте отражаются в плагине без ручного импорта.
- Смена аккаунта не оставляет чужую библиотеку; отзыв устройства обнаруживается при следующем успешном обращении/истечении офлайн-допуска.
- Неполный ответ, таймаут, 429 и несовместимая версия не уничтожают исправные данные и не создают бесконечный цикл запросов.
- При синхронизации во время формы старый текст не вставляется.
- В целевом интерфейсе нет независимой локальной библиотеки и фиктивных рабочих кнопок синхронизации; полноценный редактор «Мои» связан с аккаунтом панели.
- Настройки явно показывают источник и область хранения. Логи не содержат секреты, содержимое переписки, значения полей или тела шаблонов.
- Сообщения и команды в Discord по-прежнему не отправляются плагином.

## 10. Что нужно получить от разработчика сайта

Действующие схемы FAQ/личных шаблонов и настроек; возможности существующего входа устройств; стабильные ID; правила проектов и владельцев; решение по офлайн; формат отзыва/продления; контракты ошибок и лимитов; тестовый аккаунт или обезличенные fixtures; адрес тестового окружения. Новые маршруты предпочтительно описать OpenAPI или эквивалентной документацией с примерами.

Для уточнения дизайна достаточно адреса нужной страницы и доступа через уже авторизованный браузер либо скриншотов. Cookie не включать в ТЗ и не превращать в механизм подключения плагина. Само изучение сайта остаётся read-only; это ТЗ не является разрешением выполнять API-записи на действующей панели.

## 12. Порядок работ и критерий готовности продукта

Подготовка этого ТЗ идёт сейчас, чтобы разработчик сайта мог работать параллельно. Это не означает, что интеграция уже сделана или что прежние этапы B/C исчезли.

1. Согласовать внешний вид разделов «Настройки» и «Мои», реальные возможности сайта и контракт API с его разработчиком.
2. Завершить техническую подготовку текущего ядра (зависимости и документация), сохраняя маркировку локального прототипа.
3. Реализовать настройки и личный редактор с адаптером источника; до готовности API использовать явно обозначенные тестовые данные, не обещать сохранение на сайт.
4. Реализовать и принять подключение, CRUD и двустороннюю синхронизацию с готовым API. Затем убрать независимый локальный источник из пользовательской сборки.
5. Отдельно принять B (звуки, напоминания, подсказки), экран статистики и BD-адаптер согласно согласованному объёму. D остаётся заметкой.

Наличие работающей вставки и закрытой приёмки локального прототипа не означает готовность всего продукта из 11 пунктов. Реализованные экраны, интеграция и приёмочные результаты должны отмечаться отдельно.

## 13. Уточнения после авторизованного изучения сайта 15.10

Подробные наблюдения: [исследование панели](audits/2026-10-15-panel-live-study.md). Изучен интерфейс, а не сетевой контракт.

- Личная библиотека показана в FAQ и на отдельной странице «Шаблоны». Подтвердить единый канонический ID и источник; не синхронизировать эти представления как независимые записи.
- Общий для MJ/RO шаблон должен иметь один ID и одну версию, а не две копии.
- Папки сайта также содержат настройки браузерного расширения: триггер, отправку, автокомплит, сайты и фильтр заголовка. Плагин использует группировку и не активирует отправку сообщений.
- CRUD должен поддерживать частичное обновление с контролем версии: правка текста, названия, цвета или папки сохраняет неизвестные плагину поля расширения и наследуемые параметры. Добавить это в приёмку API.
- Согласовать палитру, сериализацию команды и токенов, удаление папки и корзину. Подписи интерфейса не заменяют схему API.

## 14. Нагрузка и передача разработчику

SSE входит в v1. Команда — 20 саппортов; проверить 20 и 100 одновременных клиентов, массовое обновление и переподключение. Один поток и один запрос синхронизации одновременно на экземпляр. Полный snapshot/ETag, объединение событий, backoff и jitter. Условия и измеримые результаты приёмки — разделы 11–13 API-контракта 1.1. Проверка документации не заменяет нагрузочный тест и приёмку настоящего API.
