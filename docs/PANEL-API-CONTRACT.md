# API панели для SupportTemplates — контракт v1

Дата: 16.10.2026. Редакция: 1.1. Владелец согласовал продуктовую схему подключения, сроки сессии, обновления и отзыв доступа. Маршруты, JSON и техническая реализация передаются разработчику панели на согласование с его инфраструктурой. Это требования к будущему API, а не описание уже работающей интеграции. Сайт не изменялся.

Этот документ уточняет [продуктовое ТЗ](PANEL-INTEGRATION-SPEC.md). При расхождении по интервалам обновления, доступу к FAQ и формату API действует это предложение. Старый интервал 15 минут отменён. Источники UI: [авторизованное исследование](audits/2026-10-15-panel-live-study.md).

## 1. Результат для пользователя

Первый запуск → «Подключить панель» → браузер на panel.majestic-rp.tech/connect → существующий вход в панель, если нужен → «Разрешить» или «Отказать» → приложение получает собственный токен напрямую от API → загружает профиль, права и библиотеку → можно использовать шаблоны.

Основные FAQ актуализирует старший **на сайте**. Приложение получает изменения автоматически. Личные шаблоны пользователь создаёт, меняет, раскрашивает и раскладывает по папкам и на сайте, и в приложении; это одни записи аккаунта.

Приложение здесь — Vencord-плагин, позднее BD-адаптер. Отдельный EXE и отдельная регистрация не требуются. Плагин вставляет текст в редактор Discord, никогда не отправляет его автоматически.

## 2. Права: проверять на API, не только скрывать кнопки

| Данные/действие | Токен приложения |
| --- | --- |
| Профиль текущего сотрудника, доступные проекты | Читать разрешённые поля |
| Основные FAQ, категории, теги, статусы | Только чтение |
| Создать/изменить/удалить/поменять статус основного FAQ | Запрещено, в том числе старшему через токен приложения |
| Личные шаблоны и папки текущего аккаунта | Читать, создавать, менять, отправлять в корзину, восстанавливать |
| Чужие личные шаблоны/папки | Нет доступа |
| Права, роль, владелец записи | Клиент не назначает |
| Избранное | В v1 локально; синхронизация отдельным расширением контракта |
| Бинды, недавние, частота использования, выбор Tech, превью | Локально на устройстве |
| Автоотправка, настройки браузерного расширения | Не применять в Discord и не перезаписывать |

Scopes: `profile:read`, `faq:read`, `personal:read`, `personal:write`, `folders:read`, `folders:write`, `sync:read`. `faq:write` не выдаётся этому клиенту. Роли сайта не повышают полномочия токена приложения. Сервер проверяет владельца и текущие права на каждом запросе, включая восстановление и получение событий.

Проекты API: `mj`, `ro`; если сайт использует `ru`, преобразование должно быть явным. EU не входит. Разрешённые проекты аккаунта пересекаются с серверами Discord: MJ 530693013622489088, RO 1089530150540034181, Tech 1395915167040016545. Tech не обходит права аккаунта; остальные серверы и ЛС выключены.

## 3. Подключение и выдача токена

Предлагается device-code flow: плагину не нужен обработчик обратного URL в Discord. Использовать стандартную семантику [RFC 8628](https://www.rfc-editor.org/rfc/rfc8628), а не передачу токена через адресную строку. Если впоследствии появится отдельное native-приложение с полноценным callback, отдельно оценить Authorization Code + PKCE. Device flow выбран здесь из-за ограничений встраиваемого плагина.

### Шаги

1. Пользователь нажимает «Подключить панель». Плагин создаёт запрос подключения. Не открывать браузер автоматически при каждом запуске.
2. Сервер выдаёт `device_code` (секрет), короткий `user_code`, ссылку подтверждения, срок 10 минут и интервал опроса 5 секунд.
3. Плагин показывает код, «Открыть панель», «Отмена» и срок ожидания. Ссылка открывается во внешнем браузере, где уже есть вход на сайт.
4. Страница /connect показывает аккаунт, название приложения, заявленное название устройства, код и точные права. Название устройства — подпись клиента, не доказательство подлинности. Пользователь сверяет код и нажимает «Разрешить»/«Отказать». Если входа нет, сайт использует свой существующий вход и возвращает к подтверждению. GET ссылки сам по себе не даёт согласия; подтверждение защищено CSRF.
5. Плагин опрашивает token endpoint с секретным `device_code`. При разрешении API возвращает токены **плагину**, браузер показывает «Готово, вернитесь в Discord». Ни access token, ни refresh token в браузерный URL не попадают.
6. При отказе/истечении плагин прекращает опрос. При отмене закрывает запрос и прекращает опрос; позднее согласие не должно незаметно подключить закрытую попытку. Новая попытка получает новый код.
7. После токена: GET /me, затем полный снимок. До успешной атомарной загрузки библиотека не считается готовой. Если права отсутствуют, показать причину, не подставлять старый аккаунт.

```mermaid
sequenceDiagram
    actor U as Саппорт
    participant P as Плагин
    participant B as Браузер панели
    participant A as API панели
    U->>P: Подключить панель
    P->>A: Создать запрос устройства
    A-->>P: device_code, user_code, ссылка
    P->>B: Открыть /connect с user_code
    B-->>U: Аккаунт, код, права; Разрешить / Отказать
    U->>B: Разрешить
    B->>A: Подтвердить под сессией сайта
    P->>A: Опрос с device_code
    A-->>P: access_token + refresh_token
    P->>A: Профиль и снимок библиотеки
    A-->>P: Разрешённые FAQ и личные данные
    P-->>U: Подключено, библиотека готова
```

### Предлагаемые auth endpoints

OAuth-запросы — `application/x-www-form-urlencoded`; ответы — JSON. Ниже JSON показан только для ответов.

| Метод/путь | Что передаёт клиент | Что возвращает сервер |
| --- | --- | --- |
| POST /oauth/device_authorization | client_id=supporttemplates, scope; расширения device_name, platform=vencord или bd, app_version | device_code, user_code, verification_uri, verification_uri_complete, expires_in, interval |
| POST /oauth/token | client_id, grant_type=urn:ietf:params:oauth:grant-type:device_code, device_code | Токены либо стандартная ошибка ожидания |
| POST /oauth/token | client_id, grant_type=refresh_token, refresh_token | Новая пара токенов |
| POST /oauth/revoke | token, token_type_hint, client_id | Успешный отзыв сессии устройства |
| POST /api/plugin/v1/device-requests/cancel | device_code в теле; это отдельное расширение протокола | 204; отменённая попытка не выдаёт токены |

```json
{
  "device_code": "<secret-random-code>",
  "user_code": "ABCD-EFGH",
  "verification_uri": "https://panel.majestic-rp.tech/connect",
  "verification_uri_complete": "https://panel.majestic-rp.tech/connect?user_code=ABCD-EFGH",
  "expires_in": 600,
  "interval": 5
}
```

```json
{
  "access_token": "<secret>",
  "token_type": "Bearer",
  "expires_in": 900,
  "refresh_token": "<secret>",
  "scope": "profile:read faq:read personal:read personal:write folders:read folders:write sync:read"
}
```

Ошибки опроса: authorization_pending — продолжить; slow_down — увеличить интервал минимум на 5 секунд; access_denied / expired_token — прекратить. При timeout увеличить паузу, соблюдать общий срок. Одновременно один опрос. При потере ответа с уже выданным токеном безопасный базовый вариант — новая попытка подключения, а не повторная неограниченная выдача секретов.

### Сессии устройства

Согласованные сроки: access 15 минут; сессия продлевается refresh до 30 дней без активности, абсолютный предел 90 дней от первоначального разрешения. Успешный refresh обновляет срок неактивности, но не сдвигает абсолютный предел. Это продуктовые параметры, не требования стандартов. Refresh ротируется, повтор старого refresh выявляет повторное использование и отзывает семейство. Клиент делает один refresh одновременно и атомарно сохраняет новую пару. Требования к защите refresh для публичных клиентов: [RFC 9700, §4.14](https://www.rfc-editor.org/rfc/rfc9700#section-4.14).

Плагин публичный клиент: зашитый client_secret не является секретом. Токен ограничен API панели и устройством; он не заменяет browser session и не открывает административные маршруты. На сервере проверять отзыв устройства и актуальные права даже при ещё не истёкшем access token. В панели нужен список устройств с последней активностью и кнопкой отзыва. Выход на одном устройстве не отзывает все остальные, если пользователь этого не выбрал.

Cookie панели и Discord-токен не передаются плагину. Секреты не кладутся в URL, экспорт, диагностический отчёт или обычное хранилище настроек. Перед выпуском выбрать и проверить доступное защищённое хранилище адаптера ОС; если его нет, предложить сессию только в памяти с повторным входом, а не обещать защищённое хранение в IndexedDB. Секреты в памяти работающего клиента также не защищены от другого вредоносного плагина.

## 4. Что плагин получает

Все ресурсные запросы: HTTPS, `Authorization: Bearer …`, API v1, JSON UTF-8. Даты — ISO 8601 UTC. ID и версии — непрозрачные строки, клиент их не сортирует и не вычисляет. Нельзя использовать заголовок шаблона как ID.

### GET /api/plugin/v1/me

```json
{
  "account": {"id": "account-42", "displayName": "Саппорт"},
  "device": {"id": "device-7", "name": "Рабочий компьютер"},
  "projects": ["mj", "ro"],
  "scopes": ["profile:read", "faq:read", "personal:read", "personal:write", "folders:read", "folders:write", "sync:read"],
  "permissionsRevision": "access-12",
  "schemaVersion": 1,
  "minClientVersion": "1.0.0",
  "serverTime": "2026-10-15T12:00:00Z"
}
```

Список проектов определяется сервером. Имя/роль в интерфейсе не являются источником авторизации. Не выдавать email, список сотрудников или ненужные сведения аккаунта.

### GET /api/plugin/v1/snapshot

Полный согласованный снимок разрешённых данных. `ETag` индивидуален для аккаунта, прав и представления; запрос поддерживает If-None-Match и 304. Ответы не кешируются общим CDN: `Cache-Control: private, no-cache`; auth — `no-store`. Все страницы снимка, если понадобится пагинация, закреплены за одной ревизией. Применять только полностью загруженный и проверенный снимок.

```json
{
  "schemaVersion": 1,
  "accountId": "account-42",
  "revision": "snapshot-81",
  "permissionsRevision": "access-12",
  "serverTime": "2026-10-15T12:00:00Z",
  "projects": ["mj", "ro"],
  "faq": [{
    "id": "faq-10", "version": "v7", "source": "faq", "projects": ["mj"],
    "title": "Проблемы со входом", "text": "Здравствуйте!\n[[greeting:end]]\nУкажите {{ник}}.",
    "command": "login", "color": null, "categoryId": "category-1", "tagIds": ["tag-1"],
    "status": "actual", "statusNote": null, "updatedAt": "2026-10-15T11:59:00Z",
    "webUrl": "https://panel.majestic-rp.tech/faq", "permissions": {"read": true, "write": false}
  }],
  "personal": [{
    "id": "personal-20", "version": "v3", "source": "personal", "projects": ["mj", "ro"],
    "title": "Мой ответ", "text": "Проверьте {{пункт|Первый|Второй}}.",
    "command": "check", "color": "#3b82f6", "folderId": "folder-2",
    "updatedAt": "2026-10-15T11:58:00Z",
    "permissions": {"read": true, "write": true, "delete": true}
  }],
  "folders": [{"id": "folder-2", "version": "v1", "name": "Проверки", "parentId": null}],
  "categories": [{"id": "category-1", "name": "Частые проблемы", "projects": ["mj"], "order": 1}],
  "tags": [{"id": "tag-1", "name": "Вход", "projects": ["mj"]}],
  "policy": {"pollIntervalSeconds": 60, "freshnessSeconds": 30, "offlineFaqInsert": false},
  "limits": {"titleLength": 160, "textLength": 20000, "commandLength": 40, "folderNameLength": 80}
}
```

Поля и правила:

- Массив projects непустой; общая запись имеет один ID и два проекта. Сервер возвращает только разрешённую проекцию записи; частичное изменение не должно удалять её недоступные клиенту связи. Для общей записи и ограниченного аккаунта API либо разрешает безопасную правку по своей политике, либо возвращает write=false; клиент не угадывает права.
- Внутренний null-проект прототипа при адаптации заменяется явной областью проектов. FAQ и персональные записи никогда не смешиваются только по названию.
- FAQ из `/faq` и личные записи из двух экранов сайта не должны дублировать одну сущность. Сервер подтверждает канонические ID и схему связи.
- folderId — личная группировка; categoryId — категория FAQ; tagIds — отдельные теги. Не сводить их в одно поле.
- Основные FAQ: actual, needs_review, outdated; архив/корзина отсутствуют в рабочем снимке. В UI два последних статуса требуют подтверждения по текущей логике. Для срочного запрета применения сервер исключает запись из активного снимка; одного предупреждения outdated для запрета недостаточно.
- Полный снимок авторитетен: отсутствующий старый ID удаляется из рабочего набора. Бинд/недавние не восстанавливают его из старого кэша. Отдельная корзина не попадает в поиск вставки.
- Основной текст передаётся с разметкой и маркерами без подстановки. Не исполнять HTML/скрипты. Плагин отображает безопасное подмножество разметки.
- Согласовать с сайтом грамматику: {{имя}}, {{имя=значение}}, {{имя|а|б}}, {{date}}, {{time}}, сдвиги ±N m/h/d/w, {{clipboard}}, {{selection}}, {{url}}, {{title}}, [[greeting:end]]. Значения полей/буфера не возвращаются на сайт. Маркер {|} сохраняется как текст схемы, но его позиционирование адаптер Discord пока не поддерживает.
- Цвет null или один из восьми HEX: #ef4444, #f97316, #eab308, #22c55e, #14b8a6, #3b82f6, #8b5cf6, #ec4899. Подтвердить совпадение с палитрой сайта.
- Команда без префикса; до 40 букв/цифр/_/-. Предлагается нормализация регистра и явная ошибка конфликта в пересекающейся области проектов; конфликт с командой FAQ разрешать переименованием личной команды. Поведение существующих дубликатов согласовать до миграции.
- Лимиты из прототипа не сокращают существующие данные сайта молча: согласовать пределы и единицу длины (в текущем JS — UTF-16 code units). Слишком длинная существующая запись остаётся читаемой или получает явную ошибку совместимости, не обрезается.
- Если вложенность папок нужна, согласовать глубину и защиту циклов; для v1 предлагаем плоские папки, parentId=null.
- Счётчики общего использования сайта необязательны и могут быть read-only расширением. Локальные нажатия на шаблоны не отправляются на панель.

## 5. Что плагин отправляет

Только запрос подключения/обновления токена, версии приложения и схемы, подтверждённые пользователем изменения личных данных, запросы чтения, версии/ETag для синхронизации и отзыв своего устройства.

Не отправляет переписку тикетов, идентификаторы просматриваемых каналов без отдельной необходимости, содержимое буфера/выделения, значения заполненных полей, локальную историю использования, cookies или Discord-токен. Сохранённый пользователем текст личного шаблона, разумеется, передаётся сайту как содержимое этой записи.

### CRUD

| Метод/путь под /api/plugin/v1 | Операция |
| --- | --- |
| GET /personal/{id} | Получить свою актуальную запись и ETag |
| POST /personal | Создать личный шаблон |
| PATCH /personal/{id} | Изменить переданные поля |
| DELETE /personal/{id} | Переместить в корзину |
| POST /personal/{id}/restore | Восстановить из корзины |
| GET /trash | Своя корзина, пагинация с cursor |
| POST /folders | Создать папку |
| PATCH /folders/{id} | Переименовать папку |
| DELETE /folders/{id} | Удалить папку, атомарно переместив записи в «Без папки» |
| GET /sync/events | Поток уведомлений об изменениях |

Для v1 восстановление папки отдельной сущностью не требуется: удаление папки не удаляет её шаблоны. Это уточняет более раннее общее предложение об одинаковой корзине для папок и записей. Срок хранения удалённых шаблонов предлагается 30 дней; сервер сообщает purgeAt. Постоянное удаление из приложения не требуется.

Пример создания:

```http
POST /api/plugin/v1/personal
Authorization: Bearer <token>
Idempotency-Key: <uuid>
Content-Type: application/json
```

```json
{"title":"Мой ответ","text":"Здравствуйте, {{ник}}!","projects":["mj"],"command":"myanswer","color":"#3b82f6","folderId":null}
```

Сервер возвращает 201, Location, ETag записи и нормализованную запись с ID/version/updatedAt/permissions. Владелец берётся из токена. Клиентские ownerId, source=faq, permissions, status, version назначения отвергаются. Разрешённые поля PATCH: title, text, projects, command, color, folderId. PATCH не заменяет объект целиком: неизвестные плагину настройки расширения, сайты, автокомплит, автоотправка и параметры папок сохраняются.

Для PATCH/DELETE/restore обязателен If-Match с ETag записи; без него 428. При изменённой версии 412 и актуальные version/ETag, затем GET записи. Если доступ уже потерян, не возвращать её содержимое. Не повторять конфликт автоматически с новой версией. UI предлагает сравнение и явное сохранение своей версии, принятие серверной или создание копии; несохранённый текст не исчезает. Любое принудительное сохранение снова использует актуальный If-Match.

Idempotency-Key обязателен для создания и рекомендуется для всех записей; область — аккаунт + операция + маршрут. Сервер хранит результат минимум 24 часа; тот же ключ с другим телом → 409. Повтор после потери ответа возвращает тот же результат, не новую запись. Очередь старше окна идемпотентности не повторяет создание вслепую: нужна сверка результата либо явное решение пользователя. После записи сервер возвращает запись, клиент запрашивает синхронизацию; уведомление другим устройствам отправляется после коммита транзакции.

Редактор показывает «Сохранено на сайте» только после ACK. Без сети — «Черновик на этом устройстве, не синхронизирован». Черновики и очередь строго привязаны к accountId; смена аккаунта никогда не отправляет старую очередь новому владельцу.

## 6. Доставка изменений FAQ и личной библиотеки

### Согласованный режим v1

| Механизм | Требование |
| --- | --- |
| Начальная загрузка | Сразу после подключения и каждого запуска |
| Быстрое обновление | SSE-уведомление после изменения, цель применения до 5 секунд при исправной сети |
| Страховочная проверка | Условный GET snapshot каждые 60 секунд с jitter ±10 секунд, даже при открытом SSE |
| Возвращение из сна/сети | Немедленная проверка, затем восстановление потока |
| Открытие окна/перед вставкой | Если последняя успешная проверка старше 30 секунд — сначала обновить |
| Ручное обновление | Кнопка «Обновить сейчас» |

Ожидаемое время при нормальной сети — 1–5 секунд; критерий приёмки p95 не более 5 секунд от коммита изменения до применения снимка подключённым клиентом. Это цель для измерения, не гарантия интернета. SSE входит в согласованный выпуск v1; один polling не является эквивалентом согласованной реализации. Резервный polling создаёт около N/60 запросов в секунду без учёта дополнительных проверок перед вставкой.

### Поток событий

GET /sync/events, Content-Type: text/event-stream. Авторизация заголовком Bearer. В реализации плагина использовать потоковый fetch/подходящий транспорт, позволяющий этот заголовок; обычный EventSource не даёт произвольный Authorization. Не помещать токен в query URL.

```text
id: event-901
event: library.changed
data: {"revision":"snapshot-82","resources":["faq"]}
```

Возможные события: library.changed (faq/personal/folders/categories/tags), permissions.changed, session.revoked, resync.required. Поток персонализирован по аккаунту/доступу, без текстов шаблонов и чужих данных. Событие — сигнал перечитать источник, не сама запись и не разрешение использовать её.

После сигнала ставится dirty и объединяются близкие события за 300 мс. Одновременно максимум одна синхронизация; если событие пришло во время загрузки, после неё выполнить ещё одну условную проверку. Повтор/перестановка событий не откатывает данные. Клиент передаёт Last-Event-ID; сервер либо воспроизводит пропущенное за свой срок хранения, либо выдаёт resync.required. После переподключения в любом случае проверить snapshot, чтобы закрыть гонку между первым снимком и подпиской.

Heartbeat каждые 20–30 секунд поддерживает соединение, но **не подтверждает свежесть библиотеки**. Истечение access token завершает поток; один refresh и повторное подключение. При отзыве сервер разрывает активные потоки и запрещает последующие чтения. Временный разрыв не удаляет кэш.

### Что видит саппорт при правке старшим

1. Старший сохраняет основной FAQ на сайте.
2. В одной транзакции меняются текст, версия записи и ревизия библиотеки. После коммита событие приходит плагину.
3. Плагин загружает актуальный снимок и атомарно заменяет рабочую библиотеку. Открытый список и превью отражают новую версию; при необходимости показывается ненавязчивое «Шаблоны обновлены».
4. Если старая версия уже была выбрана для формы/меню/собираемого ответа, вставка отменяется с «Шаблон обновился, выберите его снова». Нельзя молча подменить текст уже подтверждаемой операции. Изменения редактора личного шаблона сохраняются как черновик и получают конфликт, а не стираются обновлением.
5. Если старый текст уже вставлен в редактор Discord, плагин не переписывает черновик и не отправляет его. Можно показать уведомление об изменении источника, если такая связь ещё известна. Уже отправленные сообщения не меняются.

Для v1 безопасно отменять все ожидающие вставки/compose при изменении снимка через поколение данных, как уже делает ядро. Более точечное сохранение операций при нерелевантных изменениях — отдельное улучшение. Ответ 304 не меняет поколение.

## 7. Свежесть перед вставкой и отсутствие сети

Согласованная политика: FAQ можно читать из кэша, но вставлять только при подтверждённой свежести не старше 30 секунд и действующей сессии. При dirty, изменении прав или после сна требуется проверка независимо от времени. Политика относится ко всем путям: окно, бинд, Alt+N, inline и собранный ответ.

Последняя успешная проверка — валидный полный ответ или 304 после проверки сервером прав, не просто наличие сети/heartbeat. Для расчёта возраста использовать монотонные часы в процессе; после перезапуска/сна обязательно перепроверять. Не продлевать freshness по ошибке или старому ответу параллельного запроса.

Если проверка не удалась, не вставлять устаревший FAQ, показать «Не удалось проверить актуальность» и повтор. Личные записи тоже требуют действующего доступа: для первой версии предлагаем такую же проверку, оставляя возможность редактировать привязанный к аккаунту черновик офлайн. Более мягкий офлайн для личных шаблонов можно согласовать отдельно.

При подтверждённом отзыве: отменить вставки, закрыть рабочую библиотеку, удалить токены и кэш; не передавать несохранённые правки под другим аккаунтом. Политику удаления приватных черновиков при отзыве закрепить до выпуска; предлагаем удалить их при отзыве, а при обычном выходе сначала предложить дождаться сохранения или отказаться от них.

Строго гарантировать «ни одного старого символа» нельзя: изменение может произойти сразу после проверки, а плагин не контролирует уже вставленный черновик. Если нужна ещё более строгая защита, проверять If-None-Match перед **каждой** вставкой с ценой задержки и зависимости от сети. Рекомендация v1 — события + 30-секундная свежесть; это ограничивает окно риска, а не делает его нулевым. Для v1 согласованы события, окно свежести 30 секунд и блокировка вставки при неуспешной обязательной проверке. Запрос перед каждой вставкой не выбран.

## 8. Ошибки, совместимость и эксплуатация

Ресурсные ошибки:

```json
{"error":{"code":"version_conflict","message":"Запись изменена на сайте","fields":{},"requestId":"req-123","currentVersion":"v8"}}
```

| HTTP | Код/смысл | Реакция |
| --- | --- | --- |
| 400 / 422 | invalid_request / validation_failed | Показать конкретные поля, не терять черновик |
| 401 | token_expired | Один refresh; затем повтор допустимого запроса |
| 401 | session_revoked / invalid_token | Прекратить работу, повторный вход |
| 403 | permission_denied / project_access_denied | Не повторять запись; обновить права, не считать любой 403 отзывом всей сессии |
| 404 | not_found | Запись удалена или скрыта; не раскрывать чужое существование |
| 409 | command_conflict / idempotency_conflict | Решение пользователя |
| 412 / 428 | version_conflict / precondition_required | Сверка версий / исправление запроса |
| 429 | rate_limited | Retry-After + jitter |
| 503, timeout | временная ошибка | Ограниченный exponential backoff, сохранять исправный кэш |
| 426 | client_upgrade_required | Показать доверенную ссылку обновления, остановить несовместимые операции |

Таймаут обычного запроса предлагается 15 секунд, SSE живёт отдельно. Не создавать параллельные циклы sync/refresh при нескольких экранах. Серверные лимиты частоты и размера должны быть опубликованы. Неизвестная обязательная версия схемы блокирует применение; новые необязательные поля игнорируются, но не затираются при PATCH. Проверять типы, ID, ссылки, связи, размеры; применять снимок атомарно. Нельзя принимать ответ другого аккаунта после смены сессии.

Защита: HTTPS, лимиты выдачи/подбора кодов по IP и сессии, одноразовые попытки, CSRF на согласии сайта, токены не логировать. CORS не заменяет авторизацию; согласовать разрешённые origin desktop/browser-адаптеров и OPTIONS для Authorization/If-Match/Idempotency-Key. Избегать cookie-авторизации API плагина. Ссылки подтверждения/обновления/открытия записей проверять по доверенному origin, не принимать произвольный URL из данных.

Серверный журнал CRUD: accountId, deviceId, requestId, сущность/ID, версия до/после, время и результат; содержимое секретов и переписки не нужно. Это аудит изменений данных, **не** система поиска скриптов автозабора тикетов. Диагностика плагина: версии, время последней синхронизации, возраст данных, состояние потока, коды ошибок, без токенов и тел шаблонов.

**Разработчик панели:** device authorization, страница согласия и список устройств, токены/ротация/отзыв, серверные scopes и ownership, чтение и условные снимки, CRUD персональных записей/папок, корзина, ETag/версии/идемпотентность, сигнал изменений из всех путей редактирования сайта, SSE, ограничения и OpenAPI. Не забыть изменения прав/увольнение/архив и массовые обновления: они тоже инвалидируют снимок.

Согласованный выпуск v1: auth + me + полный snapshot/ETag + персональный CRUD/папки + серверные права + SSE + резервный polling/проверка перед вставкой. Delta API, синхронизация избранного, тикеты/статистика, обновление самого бинарника плагина — отдельные задачи. Тексты FAQ обновляются без пересборки плагина.

## 10. Приёмка API и интеграции

1. Разрешение, отказ, отмена, истечение и повтор кода; запрет получения токена только по короткому user_code; закрытая попытка не подключается позже.
2. Повторный запуск, refresh, конкурентные запросы, потеря ответа, ротация и отзыв конкретного устройства.
3. Токен обычного и старшего сотрудника не меняет FAQ ни одним API-маршрутом. Подмена ID/owner/source не открывает чужие записи.
4. Аккаунты MJ-only/RO-only/оба: снимок, Tech, общие записи и изменения прав не дают недоступных данных.
5. Создание/цвет/команда/папка/текст из плагина видны на сайте и наоборот; общий шаблон остаётся одной записью в двух проектах.
6. PATCH сохраняет браузерные настройки, неизвестные плагину. Удаление папки не удаляет текст. Корзина/восстановление соблюдают права и версии.
7. Повтор POST после timeout создаёт одну запись; изменение с сайта одновременно с плагином даёт конфликт без потери текста.
8. Изменение/удаление/архив FAQ доставляется в целевое время при исправной сети; отключённый SSE компенсируется polling. Пропущенные/повторные события и reconnect корректны.
9. Обновление FAQ во время формы, меню, compose и inline не вставляет старый текст. Уже вставленный черновик Discord не меняется.
10. Проверка старше freshness или dirty блокирует вставку до результата; offline даёт понятное сообщение, повреждённый ответ не уничтожает исправный кэш.
11. Смена аккаунта не смешивает библиотеку и очередь. Отзыв/выход отменяет ожидающие вставки.
12. Нагрузочная проверка SSE и polling на согласованном количестве пользователей; измерить p95 времени от коммита сайта до применения клиентом.
13. Логи/экспорт не содержат токены, cookies, chat text и подставленные значения. Плагин не отправляет сообщения Discord и не отправляет usage на сайт.

До начала клиентской интеграции передать: OpenAPI с примерами успешных ответов и ошибок; тестовое окружение; минимум два тестовых аккаунта с разными правами; описание канонических ID и токенов текста; лимиты; настройки CORS/прокси SSE; подтверждённые интервалы и offline-политику. Реальные пользовательские cookies в документацию не включать.


## 11. Перезапуск, увольнение и границы защиты

- Обычный перезапуск Discord не требует нового разрешения на сайте при наличии безопасно сохранённого refresh token. На старте восстановить сессию, выполнить refresh при необходимости, проверить /me и snapshot до включения вставки. Старый кэш не подтверждает актуальные права.
- Обязательная задача клиентского адаптера до выпуска: выбрать и проверить защищённое хранилище ОС. Пока оно не реализовано, обещание сохранения входа не считается выполненным. Если платформа его не предоставляет, допустим только явно обозначенный режим сессии в памяти с повторным входом.
- Увольнение/полная блокировка сотрудника на панели отзывает все его сессии устройства и семейства refresh tokens. Отменяются также незавершённые попытки подключения; повторная выдача токенов запрещена без действующих прав сотрудника.
- Сразу после фиксации блокировки сервер отказывает новым запросам, включая snapshot с If-None-Match, CRUD, refresh и SSE, даже если access token ещё не истёк. Нельзя проверять только подпись и срок JWT. Реализация должна исключить устаревший положительный кэш прав.
- Подключённым клиентам направить session.revoked и закрыть потоки. Если событие не доставлено, следующий запрос обнаружит отзыв. Разрыв SSE сам по себе не доказывает отзыв; клиент проверяет серверный код причины. Поздний ответ старой сессии не восстанавливает библиотеку после отзыва.
- Снятие одного проекта означает permissions.changed и пересборку разрешённого снимка; это не автоматический выход из остальных проектов.
- Штатный клиент после подтверждённого полного отзыва отменяет операции и очищает токены/кэш аккаунта. Удаление уже сохранённых человеком копий, скриншотов и сообщений не обещается и не является целью продукта. Серверные записи личных шаблонов не удаляются автоматически из-за отзыва устройства.
- Мгновенное изменение экрана отключённого от сети компьютера невозможно. Пока событие не получено, клиент может пользоваться последней подтверждённой свежестью в пределах 30 секунд; при dirty или обязательной неуспешной проверке вставка блокируется. Уже вставленный черновик Discord не переписывается.

## 12. Нагрузка и проверка доставки

Базовый размер команды — 20 саппортов. Считать подключённые экземпляры, а не людей: два устройства на человека дают 40 клиентов.

| Операция | Для 20 клиентов |
| --- | --- |
| SSE | 20 постоянных соединений, одно на экземпляр плагина |
| Резервная проверка | 20 запросов в минуту, около 0,33 запроса/с в среднем |
| Одно обновление FAQ | До 20 уведомлений и 20 загрузок снимка при отсутствии повторов |
| Heartbeat 20–30 с | Около 40–60 небольших сообщений в минуту |

Это расчёт частоты, а не измерение производительности сервера. Размер JSON, число аккаунтов, стоимость запросов к БД и прокси влияют на итоговую нагрузку. Полный снимок выбран для v1; delta API сейчас не требуется. Объём передачи при одном обновлении приблизительно N × размер разрешённого снимка.

Требования: один поток/цикл синхронизации/refresh на экземпляр; объединение событий за 300 мс; одна загрузка одновременно; bounded exponential backoff с jitter и Retry-After; кэш снимков/ETag с учётом аккаунта и прав, без общего кэша приватных данных. Публикация события только после коммита, из всех путей изменения: UI, массовая операция, архив, удаление, смена прав. Предусмотреть повтор доставки на сервере (например, transactional outbox); polling остаётся страховкой, а не основанием игнорировать потерю событий.

Прокси: отключить буферизацию SSE, согласовать idle timeout с heartbeat, проверить лимиты соединений и распространение событий между всеми серверными процессами. Не рассчитывать только на память одного worker, если сервис работает в нескольких экземплярах.

Нагрузочная приёмка: 20 одновременных клиентов и тест запаса на 100; реалистичный каталог; одиночное и массовое изменение; 30 минут устойчивой работы; потеря событий, 503, сон и массовое переподключение. Передать p50/p95/max доставки, ошибки, CPU/RAM, задержки API, число соединений и байты снимка. Для здоровой сети целевой p95 ≤5 с, без потери последних версий и смешивания аккаунтов. При отключённом SSE проверить резервный опрос с интервалом 50–70 с плюс время запроса. Результаты теста, а не это ТЗ, подтверждают достаточность мощности.

## 13. Что остаётся уточнить перед реализацией

Продуктовые интервалы выше согласованы. Разработчик возвращает OpenAPI, окончательные маршруты, модель хранения сессий и отзыва, лимиты и SLA инфраструктуры. Отдельно подтвердить: соответствие ru/mj; канонические ID личных записей; палитру/лимиты; срок корзины; частичные права на общие шаблоны; хранение/удаление несохранённых личных черновиков при отзыве; источник настройки префикса; защищённое хранилище на стороне адаптера. Эти вопросы не должны незаметно менять согласованные сроки или права.
