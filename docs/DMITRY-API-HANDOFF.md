# Дмитрию: API панели для Discord-плагина SupportTemplates

Дата: 16.10.2026. Единый документ для передачи разработчику.

## Коротко — что нужно от тебя

Дмитрий, я делаю Discord-плагин для саппортов. Нужна серверная часть, через которую сотрудник подключает свой аккаунт панели и получает актуальные шаблоны и данные для напоминаний.

Нужно предоставить:

1. **Вход через панель:** сотрудник нажимает кнопку в плагине, подтверждает подключение на сайте, плагин получает собственные токены. Без действующего токена рабочие API недоступны.
2. **Основные FAQ:** чтение актуальных шаблонов доступных сотруднику проектов. Из плагина основные FAQ менять нельзя, даже старшему.
3. **Мои шаблоны и папки:** чтение, создание, изменение, цвета, удаление и восстановление своих записей. На сайте и в плагине должны быть одни и те же данные аккаунта.
4. **Обновления и отзыв доступа:** изменения шаблонов автоматически доходят до плагина; увольнение или отключение устройства прекращает доступ.
5. **Данные существующей системы тикетов:** мои назначенные тикеты, начало ожидания ответа и изменения состояния. На этих данных плагин делает личные звуковые напоминания через 5/10/15 минут. Системные напоминание через 20 минут и возврат в пул через 30 минут остаются серверными.

**Это не только задача для бота.** Основной блок — API панели для входа и шаблонов. Для уведомлений нужен доступ через этот API к тому же источнику состояния, которым пользуется система тикетов. Где сейчас находятся эти данные — в панели, боте или отдельном сервисе — нужно уточнить с тобой. Переписывать работающего бота не предлагается.

Я беру на себя интерфейс и логику плагина, редактор, звук, подключение к API и клиентские проверки. От тебя нужны серверные маршруты, права, связь с существующими данными и описание контракта. Если подходящие API уже есть, лучше использовать их.

**Первый ответ, который нужен:** что уже существует, кто владеет данными тикетов и можно ли реализовать сначала вход и библиотеку, затем уведомления. Ниже — детали, чтобы не восстанавливать требования по переписке.

## 1. Статус требований и границы

- Продуктовые правила ниже согласованы с владельцем плагина.
- Маршруты, названия полей, scopes и технические сроки приведены как целевой контракт для согласования. Наличие этих маршрутов на сайте не подтверждено.
- На сайте видны FAQ, персональные шаблоны и подключение Telegram с настройками в Mini App. Это не доказывает наличие внешнего API или конкретное устройство базы.
- В плагине есть локальный демонстрационный вход. Это не подключение к production-панели. Звук новых тикетов реализован отдельно, но ещё требует живой приёмки; автоматические личные напоминания не подключены к достоверному источнику назначений.
- Плагин работает в Vencord, позднее планируется BetterDiscord. Отдельная регистрация сотрудника не нужна.
- Плагин вставляет текст в редактор Discord, не отправляет сообщения автоматически, не забирает и не возвращает тикеты самостоятельно.
- Полная статистика смен, антискрипт-логирование и подбор шаблонов по содержимому обращения не входят в первый API-релиз.

## 2. Общая схема и права

```text
Саппорт подтверждает подключение на сайте
                 |
                 v
Discord-плагин -- собственный Bearer-токен --> API панели
                                               |
                          +--------------------+-------------------+
                          |                                        |
                 FAQ и личная библиотека                 Система состояния тикетов
                                                                  |
                                                      Существующие бот / Telegram
```

API плагина можно выделить под `/api/plugin/v1/`. Это отдельный интерфейс к существующим данным, а не отдельная копия библиотеки или логики назначения тикетов. Бот продолжает работать независимо от подключения плагина.

Все рабочие запросы и поток событий требуют действующего access-токена. Исключение — публичная часть начала авторизации и обмен кодом: она не отдаёт библиотеку и защищается сроком кода, ограничением попыток и частоты запросов.

| Ресурс | Разрешение токена плагина |
| --- | --- |
| Свой профиль и разрешённые проекты | Чтение минимально необходимых полей |
| Основные FAQ, категории, теги, статусы | Только чтение |
| Свои персональные шаблоны и папки | Чтение и изменение |
| Чужие персональные шаблоны | Нет доступа |
| Свои назначенные тикеты и состояние ожидания | Только чтение, отдельное разрешение |
| Свои настройки уведомлений | Чтение и изменение, отдельное разрешение |
| Изменение основных FAQ, назначение или возврат тикета | Нет доступа |

Владелец записи и права определяются сервером по токену. Переданный клиентом `accountId` не даёт права на чужие данные. Даже если сотрудник старший, токен плагина не должен получать право редактировать основной FAQ.

Предлагаемые scopes: `profile:read`, `faq:read`, `personal:read`, `personal:write`, `folders:read`, `folders:write`, `sync:read`. Для помощника отдельно: `tickets:assigned:read`, `notifications:settings:read`, `notifications:settings:write`. Если их добавляем позднее, требуется новое явное согласие, а не незаметное расширение ранее выданного токена.

Токен разрешает действия конкретного подключения. Он не доказывает, что запрос отправлен неизменённым плагином: поэтому проверки прав обязательны на сервере для каждого запроса.

### Проекты

| Сервер Discord | Режим плагина |
| --- | --- |
| Majestic — `530693013622489088` | Majestic |
| Россия Онлайн — `1089530150540034181` | Россия Онлайн |
| Tech — `1395915167040016545` | Переключатель проектов |
| Остальные серверы и личные сообщения | Шаблоны выключены |

Переключатель Tech не расширяет права аккаунта. API отдаёт только разрешённые сотруднику проекты. В примерах используются `mj` и `ro`; соответствие кодам сайта, в частности `ru`, нужно подтвердить. EU в этом релизе не нужен.

## 3. Вход через сайт и срок подключения

Предлагается device-code flow: [RFC 8628](https://www.rfc-editor.org/rfc/rfc8628). Это позволяет подтвердить подключение в браузере без обработчика обратного URL внутри Discord.

1. Саппорт открывает меню плагина и нажимает «Войти через панель».
2. Плагин создаёт запрос подключения. Сервер возвращает секретный `device_code`, видимый `user_code`, ссылку подтверждения, срок и интервал опроса.
3. Открывается `https://panel.majestic-rp.tech/connect`. Если нужно, пользователь входит на сайт обычным способом.
4. Сайт показывает аккаунт, код, приложение и запрашиваемые права. Пользователь сверяет код и выбирает «Разрешить» или «Отказать».
5. Плагин опрашивает сервер с `device_code`. После разрешения получает `access_token` и `refresh_token` напрямую от API. Токены не передаются через адресную строку браузера.
6. Отдельный экран загрузки: профиль, права, библиотека. Только после успешной загрузки открывается меню шаблонов.

В ожидании доступны повторное открытие страницы и отмена. Отказ, истечение кода и отмена прекращают попытку; поздний ответ отменённой попытки не подключает пользователя.

| Параметр | Предлагаемое правило |
| --- | --- |
| Срок кода подключения | 10 минут |
| Опрос результата | Начальный интервал 5 секунд, далее указания сервера |
| Access-токен | 15 минут |
| Refresh-токен | До 30 дней неактивности |
| Абсолютный срок подключения | До 90 дней от первоначального подтверждения; затем новый вход |
| Перезапуск Discord | Автовосстановление через refresh-токен, если он сохранён и действителен |

При refresh сервер выдаёт новую пару токенов и аннулирует использованный refresh-токен. Повторное использование старого refresh-токена отзывает семейство токенов этого подключения. Клиент выполняет только один refresh одновременно. Продление не сдвигает абсолютные 90 дней.

Предлагаемые маршруты:

| Метод и маршрут | Назначение |
| --- | --- |
| `POST /oauth/device_authorization` | Начать подключение; `client_id`, scopes, версия плагина, название устройства |
| `POST /oauth/token` | Получить токены по device-code grant или обновить через refresh grant |
| `POST /oauth/revoke` | Отозвать своё подключение |
| `POST /api/plugin/v1/device-requests/cancel` | Отменить незавершённую попытку; доказательство владения секретным кодом |

Для ожидающего входа нужны состояния `authorization_pending`, `slow_down`, `access_denied`, `expired_token`. На `slow_down` клиент увеличивает интервал согласно стандарту. Подтверждение на сайте — защищённое от CSRF действие, не автоматическое разрешение по GET ссылки.

**Хранение токена — ответственность плагина:** защищённое хранилище ОС через проверенный desktop-адаптер. Не обычный JSON настроек, экспорт или журнал. Если такое хранение недоступно, честный резервный режим — сессия в памяти с повторным входом после перезапуска. Встроенного общего `client_secret` у плагина нет. Cookies сайта, Discord-токен и токен Telegram-бота плагину не нужны.

## 4. Что API отдаёт плагину

### Профиль и полный снимок библиотеки

`GET /api/plugin/v1/me`:

- `accountId`, отображаемое имя, ID подключения;
- доступные проекты, scopes, версия прав;
- время сервера, версия схемы, минимальная поддерживаемая версия плагина.

`GET /api/plugin/v1/snapshot`:

- `schemaVersion`, `accountId`, `revision`, `permissionsRevision`, `serverTime`;
- `projects`, `faq`, `personal`, `folders`, `categories`, `tags`;
- ограничения полей и необходимые политики, например доступные цвета и срок корзины.

Минимальная модель данных:

| Сущность | Нужные поля |
| --- | --- |
| Основной FAQ | Стабильный ID, версия, название, текст, проекты, категория, теги, статус актуальности, команда/цвет при наличии, время изменения |
| Личный шаблон | Стабильный ID, версия, название, текст, проекты, команда, цвет, ID папки или null, время изменения |
| Папка | ID, версия, название; порядок и привязка к проекту — по существующей модели сайта |
| Категория / тег | Стабильный ID, название и связь с проектом/шаблоном |

Общий шаблон — одна запись с `projects: ["mj", "ro"]`, а не две независимые копии. Редактирование меняет её и на сайте, и в плагине. Категории основного FAQ и личные папки — разные сущности.

Текст хранится без потери Markdown и переменных. Значения, которые саппорт заполняет при вставке, не отправляются обратно как изменение шаблона. Если используется граница приветствия `[[greeting:end]]`, она должна сохраняться буквально. Синтаксис переменных и ограничения текста нужно сверить с существующим редактором сайта.

Снимок полный и согласованный: отсутствие старой записи означает, что её больше нет в рабочей библиотеке. Архив и корзина не выдаются как активные FAQ. Клиент валидирует снимок целиком, затем применяет атомарно. Если нужна пагинация, все страницы должны относиться к одной ревизии.

`ETag` учитывает аккаунт и права. Ответ `304` допустим только после проверки действующей авторизации. Персональные ответы не должны попадать в общий CDN-кэш; ответы с токенами — `no-store`.

### Личные шаблоны: чтение и запись

Все пути ниже относительно `/api/plugin/v1`:

| Метод и путь | Действие |
| --- | --- |
| `GET /personal/{id}` | Своя актуальная запись и её ETag |
| `POST /personal` | Создание своего шаблона |
| `PATCH /personal/{id}` | Изменение переданных полей |
| `DELETE /personal/{id}` | Перемещение в корзину |
| `POST /personal/{id}/restore` | Восстановление |
| `GET /trash` | Своя корзина с пагинацией |
| `POST /folders` | Создание папки |
| `PATCH /folders/{id}` | Изменение папки |
| `DELETE /folders/{id}` | Удаление папки; шаблоны переходят в «Без папки» |

Пример тела создания, а не ответ существующего API:

```json
{
  "title": "Запрос логов",
  "text": "Здравствуйте, {{ник}}! Пришлите логи клиента.",
  "projects": ["mj"],
  "command": "logs",
  "color": "#3b82f6",
  "folderId": null
}
```

Сервер назначает владельца, ID, версию и время изменения. Клиент не может назначить себе `source=faq` или права. `PATCH` сохраняет неизвестные плагину поля сайта/расширения. Настройка автоотправки, если есть на сайте, не применяется в Discord-плагине.

- Для изменения, удаления и восстановления обязателен `If-Match`; нет версии — `428`, конфликт — `412`. Клиент не перезаписывает свежие изменения молча.
- Создание использует `Idempotency-Key`, чтобы повтор после потери ответа не создавал дубликат. Предлагаемое хранение результата — минимум 24 часа, область аккаунт + операция + маршрут; другой запрос с тем же ключом — `409`.
- После записи сервер возвращает нормализованную запись и новую версию. «Сохранено на сайте» показывается только после успешного ответа.
- Без сети остаётся явно обозначенный локальный черновик. Он привязан к аккаунту и не отправляется при входе другого сотрудника.
- Предлагаемый срок корзины — 30 дней с `purgeAt`; подтвердить существующую политику сайта. Постоянное удаление из плагина не требуется.

Избранное, последние 10 использованных, локальная частота использования, бинды и громкость остаются локальными в первой версии. API не получает историю использования шаблонов, буфер обмена, выделенный текст или переписку тикетов. Настройки префикса отдельно согласуем, если нужна их синхронизация.

## 5. Как приходят обновления

Предлагаемый транспорт — `GET /api/plugin/v1/sync/events`, авторизованный SSE-поток через `fetch` с заголовком Bearer. Не передавать токены в URL.

События `library.changed`, `permissions.changed`, `session.revoked`, `resync.required` сообщают, что данные изменились. После события клиент получает новый снимок; передавать всю библиотеку в каждом событии не нужно.

| Сценарий | Поведение |
| --- | --- |
| Старший обновил FAQ на сайте | После коммита сервер отправляет событие; плагин загружает и применяет снимок |
| Нормальная сеть | Целевое время 1–5 секунд; приёмочный p95 не более 5 секунд от коммита до применения |
| Потеря события | Резервная проверка каждые 60 секунд с разбросом ±10 секунд |
| Старт, выход из сна, восстановление связи | Немедленная проверка актуальности |
| Перед вставкой | Если последней успешной проверке больше 30 секунд или известно об изменении — сначала подтвердить актуальность |
| Сеть недоступна при обязательной проверке | Не вставлять неподтверждённую старую версию; показать ошибку и повтор |

SSE — основной канал первого релиза; polling — резерв. Heartbeat каждые 20–30 секунд поддерживает соединение, но сам по себе не подтверждает свежесть библиотеки. Нужны ID событий и восстановление через `Last-Event-ID` либо явный `resync.required`; после переподключения всё равно проверяется снимок.

Клиент объединяет частые сигналы примерно за 300 мс и держит один запрос снимка одновременно. Изменение во время запроса вызывает следующую проверку. Переподключение и повторы — с увеличением задержки и случайным разбросом, с соблюдением `Retry-After`. Истечение access-токена завершает поток; клиент обновляет токен и подключается снова.

Открытый список и предпросмотр обновляются. Ожидающая вставка со старой версией отменяется. Уже вставленный в редактор или отправленный текст не переписывается.

Это целевые сроки при доступной сети, а не гарантия доставки офлайн. Запрос перед абсолютно каждой вставкой не выбран; остаётся окно свежести до 30 секунд и возможность одновременного изменения на сервере.

### Нагрузка

Для 20 одновременно подключённых устройств: около 20 SSE-соединений и 20 резервных проверок в минуту, то есть примерно 0,33 запроса/с. Одна правка — до 20 уведомлений и 20 загрузок снимка. Проверки перед вставкой и записи личных шаблонов добавляются отдельно. Два устройства на сотрудника удваивают число подключений.

Это оценка количества запросов, не результат замера сервера. Нужна проверка на 20 и 100 клиентах: 30 минут работы, серия правок, массовый reconnect, p95 задержки, ошибки, CPU/RAM и размер снимка. Проверить отключение буферизации SSE на прокси и доставку событий между серверными процессами. События публиковать после коммита; потеря уведомления не должна навсегда скрывать изменение.

## 6. Увольнение, выход и ошибки доступа

- Увольнение или отключение аккаунта отзывает все его подключения, refresh-токены и ожидающие запросы входа. Новый вход запрещён.
- Отзыв одного устройства не отключает остальные устройства, если это не выбрано явно.
- После фиксации отзыва следующий запрос отвергается даже при неистёкшем access-токене. Одной проверки срока JWT недостаточно.
- Сервер уведомляет подключённый клиент и закрывает поток. При потере события отзыв обнаруживается следующим запросом.
- После подтверждённого отзыва плагин отменяет вставки и напоминания, очищает токены и рабочую библиотеку. Поздний ответ старого запроса не может восстановить доступ.
- При потере доступа только к одному проекту убираются его данные, а не обязательно весь аккаунт.
- Сбой сети не равен отзыву: не удалять данные при обычном таймауте, но соблюдать проверки свежести.
- Личные шаблоны на сервере не удаляются из-за отключения устройства. Политику несохранённых локальных черновиков при отзыве нужно согласовать отдельно.

На сайте желательно управление подключениями: список устройств, дата последней активности, отключение одного или всех. Офлайн-клиент невозможно мгновенно уведомить об увольнении. Скопированный ранее текст отозвать нельзя; защита от копирования FAQ не является целью проекта.

Ошибки API должны иметь стабильный машинный `code`, понятное сообщение, при необходимости ошибки полей и `requestId`, без токенов или внутренних стеков. Различать истёкший токен с возможностью refresh, отозванную сессию, недостаточные права проекта, конфликт записи, ограничение частоты и временный сбой. Для `429` нужен `Retry-After`; для несовместимой версии — указание минимальной версии клиента. Клиентский таймаут запроса предлагается 15 секунд.

## 7. Уведомления: две существующие системы и подключение плагина

По уточнению владельца от 16.10.2026 сейчас работают две системы:

| Система | Как работает |
| --- | --- |
| Discord-бот | Если последнее сообщение от игрока и саппорт не ответил, через 20 минут тегает саппорта. Через 30 минут без ответа возвращает тикет в общий пул. После возврата тикет может забрать любой саппорт, включая прежнего. |
| Telegram-бот | Имеет доступ к БД, проверяет последнее сообщение и отправляет саппорту личное напоминание, если игрок ждёт ответа дольше выбранного срока: 5/10/15 минут по настройке. |

**Что нужно для плагина:** предоставить авторизованный API к данным и настройкам личных напоминаний, которыми уже пользуется Telegram-система. Discord-плагин становится дополнительным каналом доставки: показывает уведомление и воспроизводит звук. Не требуется заново придумывать правила ожидания или менять Discord-систему 20/30.

Плагин получает данные через свой токен панели, без прямого доступа к БД и без токена Telegram-бота. Внутреннюю реализацию API выбирает разработчик: использовать существующий сервис либо выделить общую логику над текущей БД, чтобы Telegram и плагин одинаково определяли ожидание. Наличие готовых внешних маршрутов пока не подтверждено.

Отдельная функция — звук появления нового тикета. Это не напоминание об ожидании ответа; первый вариант реализуется по событию создания ветки Discord и не требует API Telegram-системы.

Системный бот указан владельцем: `557518046567333899`. Его тег на 20-й минуте — результат работы первой системы, а не источник раннего личного таймера. Назначение и состояние берём из БД через API.

### Правило личного ожидания

Основа по уточнению владельца; пограничные случаи и правила повторов сверяем с действующей системой:

1. Тикет назначен текущему сотруднику, игрок написал, ответа саппорта после этого нет — начинается цикл ожидания.
2. Отсчёт идёт от последнего сообщения игрока, пока после него нет ответа саппорта. При новом сообщении игрока сервер обновляет время отсчёта; прежнее предложение считать от первого неотвеченного сообщения отменено.
3. Ответ саппорта завершает ожидание. Следующее сообщение игрока после ответа начинает новый цикл.
4. Передача, закрытие или возврат в пул прекращают напоминания прежнему ответственному.
5. Повтор одного и того же уведомления после перезапуска исключается по серверному идентификатору. Повторные напоминания и изменение идентификатора после нового сообщения игрока должны следовать существующей Telegram-логике; её точное правило предоставляет разработчик.
6. Системный тег бота не сбрасывает ожидание. Наступление 30-й минуты само по себе не доказывает, что сервер уже вернул тикет.

Нужно подтвердить, как учитываются вложение без текста, ответ другого саппорта, удаление/редактирование сообщения и передача уже ожидающего тикета. Эти случаи нельзя надёжно вывести из скриншота.

### Минимальный API состояния

Предлагается `GET /api/plugin/v1/tickets/assigned` с отдельным scope. Только свои текущие назначенные тикеты разрешённых проектов; полный снимок с ETag. Отсутствующая в новом полном снимке запись отменяет локальный таймер. При пагинации обязательна единая ревизия.

Пример предлагаемого ответа; идентификаторы примера не являются реальными данными:

```json
{
  "accountId": "account-example",
  "revision": "tickets-r12",
  "serverTime": "2026-10-16T10:07:00Z",
  "tickets": [
    {
      "ticketId": "ticket-example",
      "guildId": "530693013622489088",
      "channelId": "channel-example",
      "parentChannelId": "parent-example",
      "project": "mj",
      "assigneeAccountId": "account-example",
      "state": "waiting_support",
      "waitingSince": "2026-10-16T10:00:00Z",
      "waitingCycleId": "cycle-4",
      "systemReminderAt": "2026-10-16T10:20:00Z",
      "returnToPoolAt": "2026-10-16T10:30:00Z",
      "version": "ticket-v7"
    }
  ]
}
```

Состояния должны различать `waiting_support`, `waiting_player`, `pool`, `closed`; последние два могут выражаться удалением из снимка своих назначенных тикетов. `waitingSince` и сроки могут быть `null`, когда ожидания нет. `waitingSince` обозначает время последнего сообщения игрока без ответа. Сервер предоставляет `waitingCycleId` или эквивалентный ключ дедупликации; правило его смены и повторных напоминаний согласуется с действующей Telegram-логикой. ID аккаунта панели должен явно сопоставляться с `/me`, а не подразумевать равенство Discord ID.

Изменение ожидания, назначения, закрытие и возврат должны вызывать событие в авторизованном потоке, после которого клиент перечитывает снимок. На старте и после reconnect снимок нужен до включения таймеров. Пропущенные события компенсируются резервной проверкой; можно использовать тот же интервал 60 ±10 секунд, согласовав нагрузку.

**Перед личным звуком плагин всегда проверяет актуальное назначение и ожидание через API**, даже если таймер уже истёк. Условный GET допустим. Без связи не выдаёт устаревшее напоминание как достоверное. Время привязывается к `serverTime` и монотонному отсчёту; по устаревшему снимку после `returnToPoolAt` сигнал не подаётся, сначала запрашивается состояние.

Локальная отметка аккаунт + тикет + цикл предотвращает повторы на одном устройстве. Если нужно ровно одно уведомление между несколькими устройствами или между Telegram и Discord, понадобится серверная квитанция доставки/захвата. В первую версию это не включаем без отдельного решения.

### Настройки и Telegram

Для синхронизации настроек предложены `GET/PATCH /api/plugin/v1/notification-settings` с ETag/If-Match и отдельными правами. Нужны свои `personalReminderEnabled` и `personalReminderMinutes` из 5/10/15, относящиеся к доставке в Discord. Громкость и устройство вывода остаются локальными.

Предлагается единый личный порог ожидания, который уже хранится для Telegram, и отдельные включатели доставки Telegram / Discord-плагин. Изменение общего порога из плагина должно явно отражаться в настройках и применяться к обоим каналам; включение звука Discord не включает и не выключает Telegram. Громкость остаётся локальной. Это предложение схемы синхронизации, его нужно согласовать перед реализацией.

Владелец уточнил личные варианты 5/10/15. На ранее предоставленном скриншоте Mini App были 10/15/20: разработчик должен сообщить актуальные допустимые значения и текущую схему хранения, чтобы не затереть существующие настройки. Это расхождение вариантов интерфейса, а не основание считать ожидание в Telegram другой системой правил. Личный порог не меняет системные 20/30.

Для таймера не нужны полный текст переписки, Telegram ID пользователя, токен бота или список всех сотрудников. Будущий подбор шаблонов по первому обращению требует отдельного согласования доступа к тексту и не должен незаметно расширять этот API.

Если достоверного API состояния пока нет, предпочтительно добавить чтение поверх текущей системы учёта. Не подменять назначение участием в ветке, автором первого сообщения, последним ответившим или тегом бота. До появления достоверных данных автоматические личные напоминания остаются недоступны.

## 8. Что передать разработчику плагина и в каком порядке

**Первый этап — вход и шаблоны:**

1. Согласованный контракт/OpenAPI: маршруты, JSON, scopes, статусы и ошибки.
2. Рабочий device-code flow, refresh/revoke, `/me`, снимок, личный CRUD и SSE.
3. Тестовая среда и аккаунты с разными правами: Majestic, RO, оба проекта; способ отозвать доступ.
4. Реальные ограничения текста/названий/цветов/команд, модель общих шаблонов, папок и корзины.
5. Условия подключения из Discord: допустимые origins/CORS либо согласованный desktop-транспорт, лимиты запросов и соединений. CORS не заменяет авторизацию.

**Второй этап — помощник тикетов:**

1. Подтвердить, какая система хранит ответственного и начало ожидания и кто её разработчик.
2. Согласовать перечисленные переходы состояний и точный отсчёт 20/30 минут.
3. Предоставить снимок своих назначений, события изменений и права доступа.
4. Предоставить схему существующих Telegram-настроек, допустимые интервалы и правила повторов; согласовать общий порог и отдельные каналы доставки.

Можно выпускать этапы отдельно. API шаблонов не должен ждать полной переделки уведомлений.

## 9. Приёмка

| Проверка | Ожидаемый результат |
| --- | --- |
| Нет токена / чужая запись / недоступный проект | Данные и изменение запрещены сервером |
| Разрешение, отказ, отмена, истечение кода | Каждая попытка заканчивается корректно; поздний ответ не восстанавливает отменённый вход |
| Перезапуск и refresh | Вход восстанавливается при действующем защищённо сохранённом токене; повторный refresh безопасно обработан |
| Правка FAQ на сайте | Изменение появляется автоматически в целевой срок; плагин не может редактировать основной FAQ |
| Личный шаблон изменён на сайте и в плагине одновременно | Конфликт версии виден, данные не перетираются молча |
| Потерян ответ создания, запрос повторён | Дубликат не создаётся |
| Увольнение / отзыв устройства / потеря одного проекта | Запросы и события учитывают новые права; старые ответы не возвращают доступ |
| Offline, сон, потеря SSE, 429/503 | Управляемое восстановление, без шторма запросов и неподтверждённой вставки |
| 20 и 100 клиентов | Замер задержек и ресурсов, массовое восстановление не ломает сервис |
| Личные 5/10/15, ответ до порога, тег бота, передача/закрытие/возврат | Сигнал только по актуальному своему ожиданию; ответ и потеря назначения отменяют его |
| Reload, дополнительные сообщения игрока, несколько устройств | Цикл не сбрасывается без причины; ограничения межустройственных повторов явно соблюдены |
| Изменение настройки Discord | Общий порог синхронизируется по согласованной схеме; каналы доставки независимы, системные 20/30 не меняются |
